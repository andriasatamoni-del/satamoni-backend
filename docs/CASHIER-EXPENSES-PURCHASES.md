# مصروفات ومشتريات نقدي من شاشة الكاشير (Cashier Expenses & Purchases)

المرحلة 7K استجابت لطلب المستخدم: "في الواقع في مصاريف يومية ومشتريات يومية بتطلع نقدي من الكاشير" -
قبلها كان تسجيل المصروفات والمشتريات مقصور على المدير/المحاسب/الأدمن من `satamoni-accounting.html`
بس، والكاشير معندوش أي صلاحية عليهم خالص (حتى الاطّلاع).

## القرار: تسجيل حر، اعتماد مقفول

المستخدم حدد بوضوح: الكاشير يقدر **يسجّل** مصروف/مشترى نقدي بحرية من غير أي تصريح PIN من المدير
(بعكس نظام الخصم/الإلغاء الحالي) - لكن **"الإصدار"** (اعتماد المصروف محاسبيًا، أو تأكيد المشترى) صلاحية
منفصلة تمامًا، للمدير أو المحاسب بس، عشان يقدروا يراجعوا قبل ما يتحسبوا رسميًا.

هيكل الحالات:
- **مصروف الكاشير**: بيتسجل `SUBMITTED` (مش `POSTED` زي مصروف المدير/المحاسب المباشر) - محتاج مراجعة.
- **مشترى الكاشير**: بيتسجل `PENDING` (حالة جديدة كليًا - جدول `purchases` مكانش فيه أي مفهوم حالة قبل
  كده) - محتاج مراجعة. مشترى المدير/المحاسب المباشر لسه بيتسجل `CONFIRMED` على طول، زي الأول بالظبط.

## التسجيل - مقفول بالكامل من السيرفر، مش بس بالصلاحية

`POST /api/expenses` و`POST /api/purchases` بيقبلوا صلاحية جديدة ضيقة للكاشير
(`expenses.create_own_daily`/`purchases.create_own_daily`، منفصلة عن `expenses.create`/
`purchases.create` الكاملة للمدير/المحاسب/الأدمن). لما الكاشير هو اللي بيبعت الطلب، القيم دي بتتفرض من
السيرفر نفسه (مش من الـbody المبعوت من العميل، حتى لو حاول يغيّرها):

```javascript
// routes/expenses.js
if (isCashierDaily) {
  branchId = req.user.branchId;               // فرعه بس
  businessDate = new Date().toISOString().slice(0, 10); // النهاردة بس
  supplierId = null;
  status = "SUBMITTED";                        // مش POSTED خالص
  const cashPm = await client.query(
    "SELECT id FROM payment_methods WHERE kind = 'cash' AND enabled = TRUE ORDER BY id LIMIT 1"
  );
  paymentMethodId = cashPm.rows[0]?.id || null; // كاش تلقائي - الكاشير مش بيختارها
}
```

طريقة الدفع بتتحط "كاش" تلقائيًا (مش اختيار من الكاشير) لسبب جوهري: حساب كاش الشيفت المتوقع
(`db/shift-engine.js`) بيحتاج يعرف إن المصروف/المشترى ده كاش فعلًا عشان يخصمه من الدرج - لو اتسابت
`payment_method_id` فاضية، المصروف مكانش هيتحسب في تسوية الشيفت خالص.

## المراجعة - endpoints جديدة، مقفولة على مدير الفرع/المحاسب بس

- **`POST /api/expenses/:id/review`** (جديد) - `SUBMITTED → POSTED` مباشرة (اعتماد + ترحيل محاسبي في
  خطوة واحدة). منفصل عمدًا عن `/approve` و`/post` القديمين (لسه موجودين، للمسار المحاسبي الأكمل
  الأصلي اللي محتاج `accounting.approve`/`accounting.post` - محاسب بس). صلاحية `expenses.review`
  الجديدة اتضافت لمدير الفرع والمحاسب الاتنين، مقفولة على فرع مدير الفرع بس (زي كل صلاحياته التانية).
- **`POST /api/purchases/:id/confirm`** (جديد) - `PENDING → CONFIRMED`.
- **`POST /api/purchases/:id/reject`** (جديد) - `PENDING → REJECTED`، مع سبب اختياري.
- رفض المصروف (بدل الاعتماد) بيستخدم endpoint `/:id/cancel` الموجود أصلًا من قبل - مفيش داعي لواحد
  جديد، كان بيغطي الحالة دي أصلًا (يلغي مصروف `SUBMITTED` من غير ما يحتاج قيد عكسي لأنه لسه مترحّلش).

## حساب كاش الشيفت المتوقع - من لحظة التسجيل، مش لحظة المراجعة

نقطة تصميم جوهرية: الفلوس بتخرج من الدرج **وقت ما الكاشير يسجل المصروف/المشترى**، مش وقت ما المدير
يراجعه بعدين (ممكن يفضل ساعات محتاج مراجعة). لو حساب كاش الشيفت انتظر المراجعة، هيفضل غلط طول الوقت
اللي المراجعة متأخرة فيه.

```javascript
// db/shift-engine.js - computeShiftFinancials
// المصروفات: الحالات اتوسّعت من POSTED بس لـSUBMITTED/APPROVED/POSTED، والنافذة الزمنية بقت
// COALESCE(posted_at, created_at) عشان مصروف لسه مترحّلش (posted_at لسه NULL) يتحسب بتوقيت تسجيله
WHERE e.branch_id = $1 AND e.status IN ('SUBMITTED', 'APPROVED', 'POSTED') AND pm.kind = 'cash'
  AND COALESCE(e.posted_at, e.created_at) >= $2 AND COALESCE(e.posted_at, e.created_at) <= $3

// المشتريات (جدول جديد كليًا في المعادلة): أي حالة عدا REJECTED - جدول purchases مالوش مفهوم
// "طريقة دفع" خالص (كل سطر فيه كاش نقدي بالتعريف)
WHERE p.branch_id = $1 AND p.status <> 'REJECTED'
  AND p.created_at >= $2 AND p.created_at <= $3
```

`calcExpectedCash` بقت تطرح `cashPurchasesTotal` كمان: `openingCash + cashSales - cashRefunds -
cashExpensesTotal - cashPurchasesTotal`. المصروفات كانت محتاجة عمود `expenses.created_at` من الأساس
(كان ناقص خالص - الجدول كان فيه `posted_at` بس، `NULL` لحد ما يترحّل) - اتضاف في الترحيل.

**لو المدير رفض مشترى بعدين**: بيتشال من حساب الكاش المتوقع فورًا (مش معتبر خروج كاش حقيقي بعد
الرفض) - لو العدّ الفعلي للدرج فضل ناقص بنفس المبلغ، هيظهر كفرق كاش وقت القفل، وده الإشارة الصح إن
فيه حاجة محتاجة تحقيق (بدل ما نفترض إن الرفض معناه الفلوس رجعت للدرج لوحدها).

## الواجهة

- **`satamoni-pos.html`**: زرار "🧾 مصروف/مشترى" جنب زرار الشيفت في التوب بار. مودال بتابين
  (مصروف/مشترى)، فورم بسيط (بند/نوع + مبلغ + ملاحظات اختيارية) - مفيش اختيار فرع أو تاريخ أو طريقة
  دفع خالص، كله مقفول تلقائي. بعد التسجيل بيظهر تأكيد "في انتظار مراجعة المدير/المحاسب" + قايمة
  "مصروفات ومشتريات النهاردة" بحالة كل واحدة (محتاج مراجعة / تمت المراجعة). نافذة معاينة قفل الشيفت
  اتضافلها صف "مشتريات كاش" جنب "مصروفات كاش" الموجود أصلًا.
- **`satamoni-accounting.html`**: تبويبي المصروفات والمشتريات الموجودين اتضافلهم عمود "الحالة"
  (بادچ) وعمود إجراء - زرار "✅ مراجعة واعتماد" للمصروفات `SUBMITTED`، وزرارين "✅ تأكيد"/"❌ رفض"
  للمشتريات `PENDING`، ظاهرين بس لمدير الفرع/المحاسب/الأدمن.
