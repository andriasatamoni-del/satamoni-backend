# دليل النشر للإنتاج (Satamoni Backend)

هذا الدليل موجّه للشخص اللي هيرفع السيرفر ده على استضافة حقيقية لأول مرة، أو هيتعامل معاه بعد كده
(نشر تحديث، عملية طوارئ، إضافة فرع جديد). كل الخطوات هنا اتفحصت فعليًا في بيئة تطوير/اختبار
(Jest + Postgres حقيقي)، مفيش أي خطوة هنا اتفّذت ضد بيئة إنتاج حقيقية فعليًا في المرحلة دي.

## 1. البنية المعمارية

- **Node.js + Express** - سيرفر واحد stateless (مفيش session state محلي - الهوية كلها عن طريق JWT +
  قراءة صلاحيات فريش من القاعدة في كل طلب، راجع `middleware/auth.js`). ده معناه ممكن تشغّل أكتر من
  نسخة (instance) وراء load balancer من غير أي تنسيق إضافي بينهم.
- **Postgres واحدة مركزية** لكل ما يخص الفرع/الفروع اللي بتتصل بيها مباشرة (POS، المحاسبة، المخزون).
  فيه مسار مزامنة اختياري منفصل (`routes/sync.js`، `SYNC_API_KEY`) لسيناريو "فرع بقاعدة بيانات محلية
  خاصة بيه بيزامن لسيرفر مركزي" - مش مفعّل افتراضيًا ومش جزء من مسار النشر الأساسي.
- **الواجهات الثابتة** (`public/*.html`) بتتقدّم من نفس Express server نفسه (`express.static`) - مفيش
  CDN أو استضافة منفصلة مطلوبة، بس ممكن تتحط وراء CDN لاحقًا لو الحمل كبر.

## 2. متطلبات التشغيل

- **Node.js**: اتفحص على Node 22 (v22.22.2) في بيئة التطوير - أي نسخة LTS حديثة (18+) متوقع تشتغل
  عادي (مفيش استخدام لميزات Node حديثة جدًا)، بس النسخة المفحوصة فعليًا هي 22.
- **PostgreSQL 13 أو أحدث** - إجباري (مش اقتراح): الـschema بيستخدم `gen_random_uuid()` كـdefault
  على أعمدة `sync_uuid` (راجع `db/schema.sql`) وده متضمّن في core الـPostgres من إصدار 13، من غير أي
  extension إضافي. نسخة أقدم من 13 هترمي خطأ عند تطبيق الـschema.
- **pg_dump / pg_restore** لازم يكونوا متاحين على أي جهاز/container هيشغّل سكريبتات النسخ الاحتياطي
  (`db/backup.js`, `db/restore-drill.js`) - تفاصيل كاملة في [`docs/BACKUP_AND_RECOVERY.md`](./BACKUP_AND_RECOVERY.md).

## 3. متغيرات البيئة

كلها بتتفحص فعليًا عند إقلاع السيرفر (`db/env-validation.js`، مربوطة في `server.js`) - لو في متغير
إجباري ناقص، السيرفر بيرفض يشتغل ويطبع رسالة واضحة بدل ما يشتغل "شكله تمام" ويفشل في أول طلب حقيقي.

| المتغير | إجباري؟ | الوصف |
|---|---|---|
| `DATABASE_URL` | **إجباري** | رابط اتصال Postgres كامل (`postgresql://user:pass@host:port/db`) |
| `JWT_SECRET` | **إجباري** | قيمة سرية عشوائية طويلة (32+ حرف يُفضّل) لتوقيع جلسات الدخول - **لازم تتغيّر عن أي قيمة افتراضية/اختبار قبل الإنتاج** |
| `NODE_ENV` | مُستحسن | `production` في الإنتاج - بيتحكم في: منع cross-origin افتراضيًا (CORS)، تفعيل `Strict-Transport-Security`، إخفاء تفاصيل أخطاء 500 الداخلية عن العميل |
| `PORT` | لا | البورت اللي السيرفر بيسمع عليه (افتراضي 4000) |
| `CORS_ORIGINS` | مُستحسن في الإنتاج | قايمة origins مفصولة بفاصلة مسموح لها تستدعي الـAPI (لو الواجهة الأمامية بتتقدّم من origin مختلف عن الـbackend نفسه). لو الواجهة بتتقدّم من نفس origin السيرفر (الوضع الافتراضي - `public/`) مش لازمة أصلًا |
| `DB_POOL_MAX` | لا | أقصى عدد اتصالات pg pool (افتراضي 20) |
| `DB_POOL_IDLE_TIMEOUT_MS` | لا | مهلة إغلاق اتصال idle (افتراضي 30000) |
| `DB_POOL_CONNECTION_TIMEOUT_MS` | لا | أقصى وقت انتظار للحصول على اتصال (افتراضي 5000) |
| `SLOW_REQUEST_THRESHOLD_MS` | لا | حد تنبيه الطلبات البطيئة في اللوج (افتراضي 1000) |
| `LOGIN_MAX_ATTEMPTS` / `LOGIN_LOCKOUT_MINUTES` | لا | إعدادات قفل تسجيل الدخول بعد محاولات فاشلة متكررة |
| `SYNC_API_KEY` | لا (إجباري بس لو استخدمت المزامنة) | مفتاح مشترك ثابت لمزامنة فرع↔مركزي - المزامنة معطّلة تمامًا من غيره |
| `DB_SSL` | لا (إجباري فعليًا لأي قاعدة بيانات مُدارة سحابية زي Render/RDS) | `true` بيفعّل `ssl: { rejectUnauthorized: false }` على pg Pool (`db/pool.js`) - افتراضي `false` (بدون SSL، مناسب لقاعدة بيانات محلية). من غيره، الاتصال بقاعدة سحابية مُدارة بيفشل غالبًا لأنها بترفض اتصال بدون SSL افتراضيًا |
| `BACKUP_DIR` / `BACKUP_DAILY_RETENTION_DAYS` / `BACKUP_MONTHLY_RETENTION_MONTHS` | لا | إعدادات النسخ الاحتياطي - تفاصيل في `docs/BACKUP_AND_RECOVERY.md` |
| `ADMIN_NAME` / `ADMIN_EMAIL` / `ADMIN_PASSWORD` | إجباري بس وقت `npm run seed:admin` (أول إعداد) | راجع قسم 8 تحت |

## 4. HTTPS

السيرفر نفسه بيتكلم HTTP عادي بس (مفيش TLS termination جوه الكود). **لازم** يتحط وراء reverse proxy
أو load balancer بيوفّر HTTPS (Nginx، Caddy، أو TLS termination جاهز من مزوّد الاستضافة نفسه) قبل أي
تعرّض للإنترنت العام - التوكنات (`Authorization: Bearer`) وبيانات تسجيل الدخول بتتبعت من غير أي حماية
إضافية على مستوى الكود، الاعتماد كامل على طبقة النقل (HTTPS) لمنع أي تنصّت. `Strict-Transport-Security`
header بيتفعّل تلقائيًا لما `NODE_ENV=production` (`middleware/security-headers.js`) بس ده بيفترض إن
الاتصال أصلًا HTTPS من الطبقة اللي قبل السيرفر.

## 5. عملية النشر الأول (Fresh Deploy)

```bash
# 1. استنساخ الكود وتثبيت الاعتماديات
git clone <repo-url> && cd satamoni-backend
npm install --omit=dev

# 2. إعداد .env (أو متغيرات بيئة الاستضافة مباشرة) - DATABASE_URL وJWT_SECRET إجباريين
cp .env.example .env   # لو موجود - وإلا اعمل الملف يدويًا بالمتغيرات في قسم 3

# 3. تطبيق الـschema على قاعدة بيانات فاضية جديدة (مرة واحدة بس - راجع قسم 6 لتفاصيل مهمة)
npm run migrate

# 4. أول حساب أدمن
ADMIN_EMAIL=owner@example.com ADMIN_PASSWORD=<قيمة قوية> npm run seed:admin

# 5. تشغيل السيرفر
NODE_ENV=production npm start
```

بعد التشغيل، تأكد من `GET /health` بيرجّع `{"status":"ok","db":"ok"}` قبل ما تعتبر النشر ناجح.

## 6. عملية الترحيل/التحديث (Migration Process) - ملحوظة مهمة

المشروع ده **مفيهوش نظام migrations تراكمي** (زي Flyway/Prisma migrations) - `db/schema.sql` هو تعريف
كامل للـschema بالكامل، ومصمم يتطبّق على **قاعدة بيانات فاضية جديدة بس** (`npm run migrate`). تشغيله
تاني ضد قاعدة فيها بيانات موجودة هيفشل على `CREATE TABLE` اللي أصلًا موجود.

**التبعية العملية**: أي تعديل على الـschema بعد أول نشر (عمود جديد، جدول جديد، constraint جديد) لازم
يتطبّق يدويًا على قاعدة الإنتاج عن طريق `ALTER TABLE`/`CREATE TABLE` مباشر (زي اللي متوثّق جوه
`db/schema.sql` نفسه كـALTER statements منفصلة لكل تغيير تاريخي بعد أول إصدار)، **قبل** ما يتنشر كود
بيعتمد على التغيير ده. لازم:
1. اختبار أي تعديل schema ضد نسخة من قاعدة الإنتاج (أو snapshot منها) في بيئة staging الأول.
2. تطبيق التعديل يدويًا على الإنتاج (`psql "$DATABASE_URL" -c "ALTER TABLE ..."`) في نافذة صيانة.
3. بعدين نشر الكود الجديد اللي بيعتمد على التعديل ده.
4. أبدًا العكس (نشر كود بيعتمد على عمود لسه مش موجود في قاعدة الإنتاج).

هذا القيد (مفيش migration framework) خطر حقيقي على عملية نشر متكررة - **موصى به بشدة** لأي تطوير
مستقبلي بعد الإطلاق الأول إدخال أداة migrations حقيقية (node-pg-migrate أو مشابه) بدل الاعتماد على
تعديلات يدوية موثّقة بالتعليقات.

## 7. النسخ الاحتياطي والاسترجاع

موثّق بالتفصيل الكامل في [`docs/BACKUP_AND_RECOVERY.md`](./BACKUP_AND_RECOVERY.md) - سياسة الاحتفاظ،
سكريبت `db/backup.js`، وسكريبت التحقق الدوري `db/restore-drill.js`. **لازم** يتضاف cron/scheduled task
فعلي على السيرفر (مش مثبّت تلقائيًا من الكود نفسه - راجع المستند لمثال الـcron). لو الاستضافة عندها
PITR جاهز (managed Postgres زي RDS/Cloud SQL)، فضّله كطبقة استرجاع أساسية والنسخ اليدوي هنا كطبقة تانية.

## 8. أول إعداد (First Admin Setup)

بعد `npm run migrate`، القاعدة فاضية تمامًا من غير أي مستخدم. `npm run seed:admin` (`db/seed-admin.js`)
بيقرا `ADMIN_NAME`/`ADMIN_EMAIL`/`ADMIN_PASSWORD` من متغيرات البيئة وبينشئ (أو يحدّث لو الإيميل موجود
- `ON CONFLICT DO UPDATE`) حساب أدمن واحد بصلاحية كاملة (`branch_id = NULL` - غير مربوط بفرع، زي أي
أدمن/محاسب). من بعد كده، أي مستخدم/فرع تاني بيتضاف عن طريق الواجهة نفسها (`satamoni-*.html`) أو الـAPI
مباشرة، مش سكريبتات إضافية.

## 9. إضافة فرع جديد (Branch Onboarding)

لا سكريبت منفصل - `POST /api/branches` (أدمن بس، `routes/branches.js`) بينشئ الفرع، وبعدين:
1. إنشاء مستخدم/مستخدمين للفرع بدور `branch_manager`/`cashier` (`POST /api/users` أو من شاشة الإدارة).
2. لو الفرع محتاج مطبخ مركزي منفصل، تأكيد `is_central_kitchen` مضبوط صح وقت الإنشاء.
3. ربط أصناف المخزون بالفرع (`branch_inventory_stock`) - بيتعمل تلقائيًا أول ما أي حركة مخزون تحصل
   للفرع ده (استلام بضاعة، إلخ) لو الصف مش موجود أصلًا - مفيش خطوة تهيئة يدوية إجبارية.
4. مراجعة `pos_settings` الخاصة بالفرع (لو محتاج إعدادات مختلفة عن الافتراضي).

## 10. المراقبة (Monitoring) وHealth Check

- `GET /health` - بيتحقق فعليًا من الاتصال بقاعدة البيانات (`SELECT 1` بمهلة 3 ثواني)، بيرجّع
  `200 {"status":"ok","db":"ok"}` أو `503 {"status":"degraded","db":"unreachable"}` من غير تسريب أي
  تفصيل داخلي. اربطه بأي uptime monitor (UptimeRobot، لوحة تحكم الاستضافة، إلخ) بفاصل دقيقة أو أقل.
- **تسجيل منظّم**: كل طلب بيتسجل سطر JSON واحد في stdout/stderr (`console.log`/`warn`/`error` حسب
  الحدث - راجع `middleware/request-logger.js`) - `event: "auth_failure"` لأي 401/403،
  `event: "server_error"` لأي 5xx، `event: "slow_request"` لأي طلب أبطأ من `SLOW_REQUEST_THRESHOLD_MS`.
  مفيش أي محتوى request body/query متسجّل عمدًا (حماية من تسريب باسورد/PIN/JWT بالخطأ). لو عندك مجمّع
  لوجات مركزي (ELK، CloudWatch Logs، إلخ)، وجّه stdout/stderr السيرفر عليه مباشرة - الصيغة JSON سطر
  واحد بالفعل جاهزة للفهرسة من غير أي تحويل إضافي.
- `pool.on('error', ...)` في `db/pool.js` بيسجّل أي خطأ اتصال pg على مستوى الـpool نفسه (مش بيطيح
  السيرفر) - راقب `event: "db_pool_error"` في اللوجات كإشارة مبكرة لمشاكل شبكة/قاعدة بيانات.

## 11. الإيقاف الآمن (Graceful Shutdown)

السيرفر بيستقبل `SIGTERM`/`SIGINT` (`server.js`) وبيعمل: (1) وقف استقبال اتصالات جديدة فورًا،
(2) استنى الطلبات الجارية تخلص طبيعي، (3) قفل pg pool، (4) خروج بكود `0` نظيف. فيه مهلة أمان 10 ثواني
بتجبر الخروج لو طلب عالق مش بيخلص. أي orchestrator (systemd، Docker، Kubernetes) بيبعت `SIGTERM` عادةً
عند إيقاف/إعادة تشغيل الخدمة - ده متوافق تلقائيًا من غير إعداد إضافي، بس لو الـorchestrator عنده مهلة
"grace period" قبل `SIGKILL` إجباري، خليها **أكبر من** 10 ثواني (زي 15-20 ثانية) عشان مهلة الأمان
الداخلية تاخد فرصتها كاملة الأول.

## 12. إجراء الإيقاف الطارئ (Emergency Shutdown)

لو محتاج توقف السيرفر فورًا (حادثة أمنية، خطأ حرج بيسبب ضرر):
1. **أوقف استقبال طلبات جديدة على مستوى الشبكة الأول** لو ممكن (load balancer/reverse proxy) - أسرع
   من انتظار الـprocess نفسه.
2. ابعت `SIGTERM` للـprocess (`kill -TERM <pid>` أو أمر إيقاف الخدمة العادي) - هيعمل إغلاق آمن زي
   قسم 11. استنى لحد 10 ثواني.
3. لو الـprocess معلّق ومارضيش يقفل (نادر - يبقى فيه bug حقيقي)، `SIGKILL` (`kill -9`) كملاذ أخير - ده
   مش هيقفل pg pool بنظافة، فمتوقّع اتصالات "idle" متبقية على قاعدة البيانات لحد ما Postgres نفسه
   يكتشفها بـ`tcp_keepalive`/timeout ويقفلها من عنده.
4. بعد أي إيقاف طارئ، **شغّل restore-drill أو على الأقل تأكد يدوي إن آخر عمليات محاسبية اترحّلت صح**
   (`SUM(debit)=SUM(credit)` على القيود المرحّلة - نفس الفحص اللي `db/restore-drill.js` بيعمله) قبل
   ما ترجّع الخدمة تاني، خصوصًا لو الإيقاف حصل وسط عملية بيع/دفع.

## 13. إجراء التراجع (Rollback Procedure)

- **تراجع كود بس** (مفيش تغيير schema مصاحب): ارجع لآخر commit/tag شغال (`git checkout <tag>` أو
  إعادة نشر آخر build ناجح)، `npm install`، أعد تشغيل الخدمة (SIGTERM ثم start - راجع قسم 11).
- **تراجع مصاحب لتغيير schema**: أصعب - بما إنه مفيش migration framework بيتتبّع "down migrations".
  لازم كتابة الـALTER التراجعي يدويًا (عكس أي `ALTER TABLE ADD COLUMN`/`CREATE TABLE` كان جزء من
  الإصدار ده) **قبل** ما ترجّع الكود القديم، لأن الكود القديم مش عارف يتعامل مع عمود/جدول جديد موجود -
  عادةً ده مش مشكلة (عمود إضافي زيادة مبيكسرش كود قديم بيتجاهله)، بس لو التغيير كان `NOT NULL` جديد
  أو حذف عمود، لازم مراجعة يدوية دقيقة قبل التراجع. **أفضل وقاية**: اختبار كل تغيير schema في staging
  قبل الإنتاج (نفس نصيحة قسم 6).
- **تراجع بعد بيانات اتكتبت غلط** (مش مجرد كود): ده مش "rollback" عادي - راجع
  `docs/BACKUP_AND_RECOVERY.md` لإجراء الاسترجاع من نسخة احتياطية، ووازن دايمًا بين "استرجاع كامل"
  (بيفقد أي عملية حصلت بعد وقت النسخة) و"تصحيح يدوي مستهدف" (قيد عكسي محاسبي، مش حذف مباشر - النظام
  أصلًا مصمم بمبدأ "عكس محاسبي مش تعديل" لكل عملية مالية).
