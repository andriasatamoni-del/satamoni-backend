# تجهيز الطيار واختيار الفرع (Pilot Go-Live Preparation)

مكمّل لـ`docs/PILOT-RUNBOOK.md` (يوم تشغيل عادي) و`docs/PRODUCTION-CHECKLIST.md` (نشر السيرفر نفسه) -
المستند ده لمرحلة **التحضير لمرة واحدة** قبل أول يوم طيار: اختيار الفرع، البيانات الأساسية، الأرصدة
الافتتاحية، وتسلسل يوم الافتتاح نفسه.

---

## 1) معايير اختيار فرع الطيار

قرار عمل بيخص Andrea، مش قرار تقني - القايمة دي معايير محايدة للاختيار، مش الاختيار نفسه:

- [ ] حجم طلبات يومي طبيعي (مش فرع هادئ استثنائيًا - الهدف اختبار تشغيل حقيقي مش بيئة صامتة)
- [ ] إنترنت مستقر (النظام معندوش وضع أوفلاين - راجع `docs/INCIDENT-RESPONSE.md`)
- [ ] مدير فرع متاح وملتزم بمتابعة الطيار يوميًا
- [ ] كاشير وطاقم مطبخ موجودين وقت الطيار
- [ ] تشكيلة طرق دفع تمثيلية (كاش + إلكتروني على الأقل)
- [ ] لو الفرع بيستقبل طلبات طلبات/دليفري فعليًا - أفضل لتغطية Scenario B/C في التدقيق
- [ ] هاردوير الفرع (طابعة/جهاز) جاهز فعليًا للتصديق (راجع `docs/HARDWARE-CERTIFICATION-CHECKLIST.md`)

## 2) جاهزية البيانات الأساسية (Master Data Readiness)

### الفرع
- [ ] الفرع منشئ فعليًا (`POST /api/branches`) - راجع `docs/DEPLOYMENT.md` قسم 9 للخطوات الكاملة
- [ ] `is_central_kitchen` مضبوط صح لو الفرع سنتر كيتشن
- [ ] `pos_settings` الخاصة بيه مراجعة (طرق دفع مفعّلة، حدود خصم، حدود فرق كاش)

### المستخدمون (لكل مستخدم طيار)
- [ ] الدور صحيح (`admin`/`branch_manager`/`accountant`/`cashier`/`callcenter`/`driver`)
- [ ] مربوط بالفرع الصح (`branchId`)
- [ ] الحساب فعّال (`is_active = true`)
- [ ] الصلاحيات مطابقة للمسؤولية الفعلية (راجع `middleware/permissions.js` - `ROLE_PERMISSIONS`)
- [ ] كل مستخدم له باسورد فردي قوي - **لا حسابات مشتركة** (نفس تحذير `docs/PRODUCTION-CHECKLIST.md#٦-الأمان`)
- [ ] **لا تكتب أي باسورد حقيقي في مستند/كود** - يتسلّم شفهيًا/قناة آمنة منفصلة

### الأصناف والوصفات
- [ ] المنيو الفعلي مستورد (`npm run import-menu` من `db/seed-data/satamoni-menu.json` - بيانات ستاموني
      الحقيقية، آمن التشغيل أكتر من مرة)
- [ ] الأسعار (`menu_item_variants.price`) مطابقة للمنيو الحالي فعليًا
- [ ] كل صنف نشط له `unit_cost` حقيقي - أي صنف من غيره هيظهر كتنبيه `ITEMS_MISSING_COST` (راجع
      `docs/ACTION-CENTER-OWNERSHIP.md`) وهيفسد أي تقرير ربحية يستخدمه
- [ ] الوصفات (`menu_item_variant_ingredients`) مربوطة صح - أي صنف مباع من غير وصفة مش هيخصم مخزون

### المخزون
- [ ] الأرصدة الافتتاحية مسجّلة عن طريق المسار الرسمي بس - **`POST /api/inventory/stock/adjust`**
      (`movementType: "adjustment"`) بملاحظة واضحة توثّق الجرد الفعلي ومين عدّه - **ممنوع تمامًا** أي
      `UPDATE`/`INSERT` مباشر على `branch_inventory_stock` (نفس التحذير الصريح في
      `docs/PRODUCTION-CHECKLIST.md#٣-ترحيل-قاعدة-البيانات`)
- [ ] الوحدات (`unit`) مطابقة بين المخزون والوصفة (كيلو/قطعة/إلخ)

### الموردون
- [ ] موردي الطيار الفعليين مسجّلين (`suppliers`)
- [ ] بيانات دفع/شروط سداد صحيحة

### العملاء
- [ ] **لا تستورد بيانات عملاء حقيقية غير ضرورية للطيار** - رقم تليفون كافٍ لأي طلب يحتاجه، بدون بيانات
      شخصية زيادة عن الحاجة التشغيلية

## 3) الأرصدة الافتتاحية (Opening Balances)

| البند | كيف يتسجل | التوثيق المطلوب |
|---|---|---|
| **كاش افتتاحي** | `POST /api/shifts/open` (`openingCash`) - لكل شيفت كاشير، مش رصيد فرع عام | المبلغ + المسؤول + الوقت (النظام بيسجلها تلقائيًا وقت الفتح) |
| **مخزون افتتاحي** | `POST /api/inventory/stock/adjust` (راجع فوق) | الصنف + الكمية + الوحدة + مين عدّ + تاريخ الجرد الفعلي |
| **مديونيات موردين قائمة** | فقط لو محتاجة تظهر في الطيار - سجّلها كفاتورة مورد حقيقية (`supplier_invoices`) بتاريخها الأصلي | رقم فاتورة المورد الحقيقي (منع تكرار على مستوى القاعدة) |
| **أرصدة عملاء/طلبات قائمة** | فقط لو مطلوب تشغيليًا - لا تخترع بيانات | - |

**لا تُدخل أي رصيد افتتاحي بصمت** - كل رقم فوق لازم يتوثّق مين سجّله ووقتها، عشان أي تحقيق لاحق يقدر
يميّز "رصيد افتتاحي موثّق" عن "حركة تشغيلية عادية".

## 4) فحص الأجهزة (Device Check)

مُغطّى بالكامل في [`docs/HARDWARE-CERTIFICATION-CHECKLIST.md`](./HARDWARE-CERTIFICATION-CHECKLIST.md) -
لازم يتنفّذ كامل ويتوقّع (تم/فشل + تاريخ + اسم الفرع) قبل اعتبار الفرع جاهز هاردوير-وار. يغطي: الطابعات
الحرارية (مسار سليم + سيناريوهات فشل حقيقية)، درج النقدية (مفيش تكامل - يدوي)، قارئ الباركود (غير
مستخدم حاليًا).

إضافة لذلك تحقق من: تسجيل دخول فعلي بكل حساب طيار (كاشير/مدير/محاسب/كول سنتر) على جهازه الحقيقي، شاشة
المطبخ (`satamoni-kds.html`) لو مستخدمة، انتهاء الجلسة (session) بيرجّع لتسجيل دخول مش يعلّق الشاشة.

## 5) يوم الافتتاح (Go-Live Day Sequence)

### T-1 يوم

      الآن، أم فيه جدولة تلقائية فعلية شغالة؟ (راجع قسم "حالة النسخ الاحتياطي" في التقرير)
- [ ] النشر مؤكد (`GET /health` = 200، الإصدار الصحيح شغال)
- [ ] الترحيلات (migrations) اتطبّقت - `SELECT * FROM schema_migrations ORDER BY id DESC LIMIT 5`
- [ ] المستخدمون/الصلاحيات/البيانات الأساسية كلها من قسم 2 فوق مؤكدة
- [ ] المخزون الافتتاحي والكاش الافتتاحي جاهزين (قسم 3)
- [ ] الأجهزة اتفحصت (قسم 4)
- [ ] الـSOPs اتوزّعت على الفريق: `docs/PILOT-RUNBOOK.md`، `docs/CASH-PAYMENT-DISCREPANCY-SOP.md`،
      `docs/ACTION-CENTER-OWNERSHIP.md`، `docs/PILOT-INCIDENT-TEMPLATE.md`
- [ ] الفريق المسؤول اتبرّف - كل حد عارف دوره ومين يتصل بيه لو حصل عطل (`docs/INCIDENT-RESPONSE.md`)

### T-30 دقيقة
- [ ] تسجيل دخول تجريبي بكل دور
- [ ] فتح شيفت تجريبي وقفله فورًا (يتأكد المسار شغال قبل أول عميل حقيقي)
- [ ] شاشة POS/KDS تحمّل صح
- [ ] عملية دفع تجريبية (لو ممكن على بيئة منفصلة، أو أول طلب حقيقي صغير)
- [ ] الإنترنت مستقر
- [ ] `GET /api/reports/action-center?branchId=<الفرع>` بيرجّع من غير خطأ (حتى لو فاضي)

مفسّرة في الواجهة (راجع "أثناء التشغيل" في `docs/PILOT-RUNBOOK.md`).

### الإقفال
نفّذ قايمة "الإقفال" الكاملة في `docs/PILOT-RUNBOOK.md`.

## 6) معايير نجاح الطيار (Success Criteria)

- لا معاملات مالية مكررة (بيع/دفع اتسجل مرتين لنفس العملية الحقيقية)
- لا حركة مخزون غير مفسّرة (كل حركة ليها سبب واضح في `inventory_movements`)
- لا وصول غير مصرّح لفرع تاني (`assertOwnBranch` سليم عمليًا زي ما هو مُختبَر كودياً)
- كل فرق كاش في شيفت اتراجع (`PENDING_REVIEW` صفر متبقي آخر اليوم)
- كل بند Action Center حرج (severity=HIGH) له مالك اتصرف فيه (راجع `docs/ACTION-CENTER-OWNERSHIP.md`)
- لا حادثة سلامة بيانات حرجة (قيد محاسبي غير متزن، رصيد مخزون سالب غير مفسَّر)
- الطلبات بتكمّل بداية لنهاية (POS → تحضير → دفع → إتمام) من غير تدخل يدوي استثنائي
- المشتريات بتكمّل بداية لنهاية (PO → استلام → فاتورة → سداد)
- تحويل السنتر كيتشن بيكمّل (إرسال → استلام) بكميات مطابقة أو فرق موثّق
- الهالك مصنّف بفئة حقيقية (مش صفر تنبيهات "من غير فئة" - راجع التحسين الأخير على `/api/inventory/waste`)
- تقارير الربحية بتفصح عن أي COGS ناقص (`cogsIncomplete`) بدل ما تبان دقيقة وهي مش كده
- الموظفون قادرون ينفّذوا العمليات الروتينية من غير تدخل Andrea الشخصي في كل استثناء عادي

## 7) قاعدة التوقف/الاستمرار (Stop / Continue)

**أوقف الطيار فورًا** لو: معاملة مالية غير موثوقة، تكرار مالي/مخزوني حقيقي، وصول غير مصرّح لفرع تاني،
سلامة بيانات القاعدة مهددة، الطلبات مش بتكمّل بشكل موثوق.

**كمّل مع تسجيل حادثة** (`docs/PILOT-INCIDENT-TEMPLATE.md`) لو: إزعاج واجهة، مشكلة تدريب، باج بسيط غير
حرج، مشكلة خدمة خارجية (طلبات/إنترنت) بحل مؤقت آمن.
