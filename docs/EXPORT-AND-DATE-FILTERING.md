# تصدير Excel وفلتر مدى التاريخ (Export & Date-Range Filtering)

المرحلة 7J غطّت طلب المستخدم: تصدير كل التقارير كـExcel، وإضافة اختيار "من - لحد" لفلترة التقارير
بمدى تاريخ مرن بدل ما تكون مقفولة على سنة/شهر بس. اتقسم الطلب لثلاث حاجات منفصلة بعد نقاش مع
المستخدم على الخيارات التقنية:

## 1. تصدير PDF - نفس شاشة الطباعة الموجودة (بدون تغيير)

قرار المستخدم: مفيش داعي لمكتبة تحميل PDF مباشر جديدة. توليد PDF عربي من المتصفح بمكتبات زي jsPDF
فيه خطر حقيقي إن النص العربي يطلع متقطّع أو مقلوب (المكتبات المتاحة مش بتدعم تشكيل الحروف العربي
صح). زرار "🖨️ طباعة" من المرحلة 7I أصلًا بيدّي نفس النتيجة بشكل مضمون 100%: المستخدم يضغط الزرار،
يختار "حفظ كـ PDF" من نافذة طباعة المتصفح - نفس محرك عرض المتصفح الحقيقي، فالعربي بيطلع صح دايمًا.

## 2. تصدير Excel - ملف CSV (مش xlsx حقيقي)

قرار المستخدم: CSV بسيط بدل xlsx منسّق، عشان يفضل من غير أي مكتبة جديدة تتضاف للمشروع (المشروع
مفيهوش أي bundler - كل صفحة سكريبتات مباشرة بـ`<script>` عادي، مش npm packages في المتصفح).
CSV بيتفتح في Excel/Google Sheets مباشرة زي أي ملف إكسل عادي.

### الآلية

`SatamoniPrint.exportCurrentTabCSV()` - نفس آلية استخراج الأقسام المستخدمة في الطباعة بالظبط
(`collectSections` من `print-reports.js`، المرحلة 7I) - نفس الجداول، نفس العناوين، بس بدل ما تتفتح
في نافذة طباعة، بتتحول لملف CSV واحد ينزل على جهاز المستخدم مباشرة:

```javascript
// public/js/print-reports.js
function exportPanelCSV(panelEl, { title } = {}) {
  const sections = collectSections(panelEl); // نفس الدالة المستخدمة في الطباعة بالظبط
  const lines = [];
  sections.forEach((s, i) => {
    if (i > 0) lines.push("");
    if (s.heading) lines.push(csvEscape(s.heading));
    lines.push(...tableToCsvRows(s.table));
  });
  downloadCsv(title, lines.join("\r\n"));
}
```

- **BOM في أول الملف** (`﻿`) ضروري عشان Excel يقرأ العربي بترميز UTF-8 صح من غير ما يتلخبط.
- زرار "📊 تصدير Excel" اتضاف جنب زرار الطباعة في كل الصفحات السبعة اللي كانت متغطية في المرحلة 7I،
  بنفس المنطق: تصدير أي تبويب مفتوح حاليًا من غير أي كود خاص بكل تقرير.
- الداش بورد (بطاقات KPI ورسم بياني، مفيش جداول) - نفس الأسلوب المخصّص من المرحلة 7I
  (`extractKpiRows`/`extractBarRows`/`extractTrendRows`) بس بيتحول لأسطر CSV بدل HTML طباعة.

## 3. فلتر مدى التاريخ (من - لحد) على كل التقارير

### القرار: كل تقرير حسب طبيعته، مش تحويل أعمى لكل حاجة

المستخدم اختار "كل التقارير مرة واحدة" - لكن البحث الأولي قبل أي كود لقى إن أغلب تقارير النظام
أصلًا بتقبل مدى تاريخ حقيقي (from/to) من زمان، عن طريق دالة مشتركة `resolveDateRange()` في
`routes/reports.js` بتقبل from/to أو year/month كاختصار بديل. الفجوة الحقيقية كانت **6 تقارير بس**
مقفولة على year/month إجباري: `daily`، `income-statement`، `income-statement/by-branch`،
`dashboard`، `vat-summary`، `accounting-reconciliation`.

في المقابل، فيه تقارير تانية *لازم* تفضل زي ما هي - مش عيب، طبيعتها كده:

- **تقارير "لحظة في الزمن" (asOf)**: ميزان المراجعة، الميزانية العمومية، تقرير الكاش، أعمار الموردين
  - رصيد "لحد تاريخ معيّن"، مفيش معنى لـ"من" فيها أصلًا.
  - **الرواتب**: `payroll.js` (ملخّص، بصمة الحضور، حضور المطبخ المركزي، السلف/الجزاءات، تشغيل الرواتب)
  - الرواتب مفهوم شهري بطبيعته في النظام - `central_kitchen_manual_attendance` و`department_sales`
    مفتاحهم الأساسي `(year, month)` فعليًا (مش عمود تاريخ يتحول لمدى)، و`computePayrollSummary`
    بيحسب "راتب الشهر ده" ككتلة واحدة، مش تجميع نشاط عبر أيام. تحويلها لـfrom/to هيدّي أرقام مش
    حقيقية. فضلت زي ما هي.
  - **لوحات تشغيلية حية**: لوحة التوزيع (يوم واحد بس - "طلبات النهاردة")، ورديات الكاشير، حضور
    الموظفين اليومي - دي مش تقارير فترة، دي حالة النهاردة، وفلتر مدى هيغيّر معناها بالكامل.
  - **عتبات زمنية مش مدى**: العملاء الخاملين ("مش طلبوا من كذا يوم")، الدفعات قريبة الانتهاء ("هتخلص
    خلال كذا يوم") - سؤال مختلف تمامًا عن "من - لحد".

### التحويل نفسه (الـ6 تقارير)

كل تقرير من الستة بقى بيقبل `from`/`to` **بجانب** `year`/`month` (مش بدالها - توافق كامل مع أي
استدعاء قديم). المنطق: لو `from` و`to` اتبعتوا، يتستخدموا؛ غير كده يترجعوا لـ`year`/`month`.

**التحدي الحقيقي**: تكلفة الرواتب (`payrollCost`) مستخدمة جوه `income-statement` و`dashboard`
لحساب صافي الربح، لكنها بتتحسب شهريًا بالكامل (مش قابلة للتجزئة على مدى جزئي - راجع الفقرة فوق).
الحل: `monthIfFullMonthRange(from, to)` بتتأكد إن المدى المختار شهر كامل بالظبط (أول يوم لحد آخر يوم
في نفس الشهر) قبل ما تجيب تكلفة الرواتب:

```javascript
function monthIfFullMonthRange(from, to) {
  const f = new Date(`${from}T00:00:00`);
  const t = new Date(`${to}T00:00:00`);
  const year = f.getFullYear();
  const month = f.getMonth() + 1;
  const lastDay = new Date(year, month, 0).getDate();
  const isFullMonth = f.getDate() === 1 && t.getFullYear() === year
    && t.getMonth() + 1 === month && t.getDate() === lastDay;
  return isFullMonth ? { year, month } : null;
}
```

لو المدى مش شهر كامل، الرد بيرجّع `payrollCost: null` و`netProfitAfterPayroll: null` مع رسالة
`note` واضحة - **مش رقم صفر ولا رقم غلط**. الواجهة بتعرض "غير متاح" بدل `0.00 ج.م` في الحالة دي
(دالة `moneyOrNA` في `satamoni-accounting.html`/`satamoni-dashboard.html`) - قرار متعمّد إن نعرض
"مش متاح" بدل ما نعرض رقم مضلّل، بدل ما نتجاهل المشكلة أو نفترض إنها صفر.

باقي أرقام التقرير (الإيراد، تكلفة البضاعة، المصروفات) بتفضل شغالة بشكل صحيح لأي مدى تاريخ، حتى لو
مش شهر كامل - المشكلة مقصورة على تكلفة الرواتب بس.

### VAT ومطابقة الحسابات - from/to اختياري إضافي، مش بديل عن الشهر

`vat-summary` و`accounting-reconciliation` مفهومهم مرتبط بشهر تقويمي حقيقي (الإقرار الضريبي شهري
بطبيعته في مصر، ومراجعة الفترة المحاسبية بتتم شهر بشهر). الواجهة فيهم لسه سنة/شهر هو الافتراضي
(نفس ما كان)، لكن اتضاف اختيار "أو مدى مخصص: من - لحد" جنبه لمين محتاج مرونة أكتر - لو اتملى المدى
المخصص، بياخد أولوية على السنة/الشهر.

### الفلاتر الموجودة أصلًا اتحسّنت شكليًا بس

فلاتر from/to كانت شغالة أصلًا من غير `<label>` قبلها في تبويبات كشف الحساب والقيود وقائمة الدخل من
دفتر الأستاذ (`satamoni-accounting.html`) وتقارير HR (`satamoni-payroll.html`) وسجل الأحداث
(`satamoni-audit.html`) - اتضافلها `<label>من</label>`/`<label>إلى</label>` عشان أداة الطباعة
(`readFilterLabels` من المرحلة 7I) تلقطها صح في الميتا المطبوعة. مفيش تغيير في السلوك، تحسين توافق بس.

## الملفات المتأثرة

**الباك إند**: `routes/reports.js` (تحويل `computeRevenueAndCogsByBranch` من `(year, month)` لـ
`(from, to)`، إضافة `monthIfFullMonthRange`، تحويل الـ6 endpoints).

**الفرونت إند**: `public/js/print-reports.js` (دوال `exportPanelCSV`/`exportCurrentTabCSV`/
`downloadCsv`/`csvEscape`/`tableToCsvRows` الجديدة)، `public/satamoni-accounting.html` (مدى مخصص
لقائمة الدخل/الضريبة/المطابقة + labels)، `public/satamoni-dashboard.html` (مدى مخصص + تصدير CSV
مخصص)، وباقي الصفحات الست من المرحلة 7I (زرار تصدير Excel بس، جنب زرار الطباعة).

**الاختبارات**: `tests/report-date-range.test.js` (جديد) - بيتأكد إن from/to والـyear/month
المكافئ ليه بيرجّعوا نفس النتيجة بالظبط على الـ6 تقارير، وإن تكلفة الرواتب null صح لمدى جزئي ومتاحة
صح لشهر كامل، وإن رفض الطلب من غير أي مدى لسه شغال.

## اختبار

442 (من المراحل قبل كده) + 8 اختبارات جديدة = 450/450، استقر عبر تشغيلتين. تحقق حقيقي بمتصفح
(Playwright): مدى تاريخ مخصص في قائمة الدخل/الضريبة/المطابقة/الداش بورد بيرجّع أرقام صحيحة،
"غير متاح" بيظهر صح لمدى جزئي بدل رقم مضلّل، تحميل CSV بمحتوى صحيح ومُرمّز عربي صح من 6 تقارير
مختلفة (قائمة الدخل، الضريبة، المصروفات، الداش بورد، مركز التقارير)، والطباعة (المرحلة 7I) لسه
شغالة صح من غير أي تأثير.
