# تأكيد الطلب بـ SMS/واتساب (SMS/WhatsApp Order Confirmations)

المرحلة 7S بتضيف تأكيد تلقائي للعميل برسالة SMS/واتساب بعد ما طلب دليفري أو تيك أواي هاتفي يتسجل -
كانت النقطة دي في قايمة "نيس تو هاف" في تدقيق المرحلة 7D. النظام مفيش عنده بيانات اعتماد حقيقية لأي
بوابة إرسال (Twilio أو غيرها)، فبدل ما نبني تكامل مع مزوّد بعينه مش نقدر نختبره فعليًا، اتبنى نفس أسلوب
`SYNC_API_KEY`/تكامل Talabat: بنية جاهزة تمامًا، مُختبرة بالكامل ضد سيرفر HTTP وهمي، ومعطّلة (No-Op)
بأمان لحد ما حد يجهّز بوابة حقيقية ويحط الـ URL بتاعها في متغيرات البيئة - وقتها هتشتغل من غير أي تعديل
كود إضافي.

## الفكرة

### `db/sms-provider.js` - إرسال عام لأي بوابة Webhook

مش مربوط بمكتبة مزوّد بعينه. أي بوابة (محلية أو دولية) بتقبل نداء HTTP بسيط (`POST`/`GET` بـ
`{to, message}`) تقدر تتوصل من غير أي تعديل كود:

- `SMS_WEBHOOK_URL` - لو مش متظبط، الدالة بترجع `{sent:false, status:"not_configured"}` من غير أي
  محاولة اتصال فعلية - عمدًا، عشان النظام يفضل شغال طبيعي قبل ما بوابة حقيقية تتجهّز.
- `SMS_WEBHOOK_METHOD` - `POST` (افتراضي) أو `GET`.
- `SMS_WEBHOOK_AUTH_HEADER` - لو متظبط، بيتبعت كـ `Authorization` header (مثلًا `Bearer xxx`).

فشل الاتصال (خطأ HTTP أو تعذّر الاتصال) بيترجع `{sent:false, status:"failed", error}` من غير ما يرمي
استثناء أبدًا.

### `db/order-notifications.js` - الاستدعاء من جوه إنشاء الطلب

`maybeSendOrderConfirmation()` بتتنادى في `routes/orders.js` **بعد الـCOMMIT مباشرة** (الطلب اتسجل
بنجاح بالفعل)، وكلها ملفوفة في try/catch بيسجل الخطأ في الـconsole بس - زي فلسفة `logAudit()` بالظبط
("أخطاء التسجيل نفسه بتتبلع هنا عمدًا... عشان تسجيل الـaudit ميكسرش عملية حقيقية"). يعني:

- فشل الإرسال (أو مفيش بوابة أصلًا) **أبدًا** مبيأثرش على نجاح تسجيل الطلب أو استجابته للكاشير.
- الأنواع القابلة للتأكيد بس: `delivery` و`takeaway` (العميل مش قدّام الكاشير يشوف الفاتورة المطبوعة -
  على عكس طلب الصالة اللي بيشوفها على الطاولة).
- الإرسال بيحصل بس لو `pos_settings.sms_confirmations_enabled = TRUE` (افتراضيًا `FALSE`).
- كل محاولة (نجحت أو فشلت أو مفيش بوابة) بتتسجل في جدول `order_notifications` للمراجعة/التتبع -
  append-only، مفيش تعديل أو حذف.

## الإعداد

- شاشة الأدمن (`satamoni-admin.html`) فيها checkbox جديد "تفعيل تأكيد الطلب بـ SMS/واتساب للعميل"
  جنب إعدادات نقطة البيع التانية (الخصم/الضريبة). بيتحفظ عن طريق
  `PATCH /api/pos-settings { smsConfirmationsEnabled }` (أدمن بس، زي باقي إعدادات نقطة البيع).
- لتفعيل الإرسال الفعلي: حط `SMS_WEBHOOK_URL` (وممكن `SMS_WEBHOOK_METHOD`/`SMS_WEBHOOK_AUTH_HEADER`)
  في متغيرات بيئة السيرفر، وفعّل الـcheckbox من شاشة الأدمن.

## اختبار

9 اختبارات جديدة تغطي: `sendMessage()` بمفردها (مفيش بوابة / بوابة شغالة بترجع البيانات صح مع
الـauth header / بوابة راجعة خطأ HTTP / تعذّر الاتصال تمامًا)، وأثرها الفعلي جوه إنشاء الطلب (الإعداد
مطفي = مفيش أي صف حتى لو دليفري/تيك أواي، الإعداد شغال بس مفيش بوابة = صف `not_configured`، الإعداد
شغال + بوابة شغالة = صف `sent` والرسالة فيها رقم الطلب والمبلغ، الإعداد شغال + بوابة فاشلة = الطلب لسه
بينجح 201 والصف بيتسجل `failed`، وطلب صالة مش بيتأثر خالص حتى لو الإعداد شغال). الفل ريجريشن 508/508
على مرتين متتاليتين.

تحقق حقيقي بمتصفح (Playwright) + سيرفر HTTP وهمي محلي كبوابة إرسال: تفعيل الـcheckbox من شاشة الأدمن،
حفظه، وتأكيد إنه فاضل متفعّل بعد إعادة تحميل الصفحة. وبشكل منفصل (عبر API مباشرة، بنفس السيرفر الفعلي
`node server.js` وقاعدة بيانات التطوير الحقيقية): إنشاء طلب تيك أواي فعلي والتأكد إن صف `order_notifications`
اتسجل بحالة `sent`، وإن البوابة الوهمية استلمت فعلًا `{to, message}` بالبيانات الصحيحة.
