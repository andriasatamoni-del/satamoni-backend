# مرتجع المشتريات (Purchase Returns)

المرحلة 7N بتضيف معاملة "مرتجع مشتريات" - إرجاع بضاعة للمورد (تالفة، غلط، منتهية الصلاحية) - كانت
دي آخر نقطة متبقية من قايمة "بعد الفتح التجريبي" في تدقيق المرحلة 7D خاصة بالمشتريات الرسمية.

## الفرق عن `/goods-receipts/:id/cancel` الموجود أصلًا

النظام كان فيه أصلًا آلية إلغاء سند استلام كامل (`POST /api/goods-receipts/:id/post` → `.../cancel`)،
لكنها بتشتغل بس لو **الدفعة كلها لسه متصرفتش خالص**. مرتجع المشتريات ده معاملة منفصلة بتسمح بإرجاع
**كمية جزئية** من صنف/دفعة معينة في أي وقت لاحق - حتى لو باقي نفس سند الاستلام اتباع أو اتصرف عادي -
من غير ما تلمس سند الاستلام أو أمر الشراء الأصليين خالص.

## سير العمل

`DRAFT` (مسودة - `purchasing.create`) → `POST /:id/post` (ترحيل فعلي - `purchasing.create` أو
`purchasing.approve`) → `POSTED` (نهائي، مفيش تراجع). مسودة لسه معملتش POST ممكن تتلغي
(`purchasing.cancel`)؛ مرتجع مُرحّل بالفعل **مايتلغيش** - البضاعة فعليًا خرجت للمورد.

عند الترحيل:
- لو السطر معاه `batchId` محدد: بيتأكد إن `remaining_quantity` في الدفعة دي كافية، بيخصمها بالظبط،
  وبيستخدم تكلفة الدفعة نفسها (`unit_cost`) - مش FEFO عبر كل الدفعات، عشان الإرجاع يبقى من نفس الدفعة
  اللي فيها العيب بالظبط.
- من غير `batchId`: خصم عادي بمنطق FEFO/FIFO القياسي (زي أي حركة مخزون تانية).
- قيد محاسبي واحد: **DR الموردون (2100) / CR المخزون (1400)** - بيقلل المديونية المستحقة للمورد، عكس
  قيد الاستلام الأصلي بالظبط.

## API

- `POST /api/purchase-returns` - `{branchId, supplierId?, goodsReceiptId?, reason, notes?, items:[{inventoryItemId, batchId?, quantity, unit, unitCost?}]}`
- `GET /api/purchase-returns?branchId=&status=&supplierId=` - قايمة (مدير فرع بدون `branchId` بيترشّح على فرعه أوتوماتيك)
- `GET /api/purchase-returns/:id` - تفاصيل + أصناف
- `POST /api/purchase-returns/:id/post` - ترحيل (idempotent - ترحيل تاني لنفس المرتجع بيرجّع `duplicate: true` من غير ما يخصم تاني)
- `POST /api/purchase-returns/:id/cancel` - إلغاء مسودة بس

كل الـendpoints بتستخدم صلاحيات `purchasing.*` الموجودة أصلًا من المرحلة 4A - مفيش صلاحية جديدة اتضافت.

## نطاق المرحلة دي - مفيش واجهة مستخدم

نظام الشراء الرسمي بالكامل (موردين/طلبات شراء/أوامر شراء/سندات استلام - المرحلة 4A) **مفيش له شاشة
frontend خالص لحد دلوقتي** - شغال API بس. مرتجع المشتريات بُني بنفس المنطق ده: معاملة API كاملة
ومختبرة، جاهزة تتربط بأي شاشة مشتريات هتتبني - بس بناء شاشة مشتريات كاملة من الصفر خارج نطاق "مرتجع
مشتريات" اللي كان مطلوب هنا، وده تحدي أكبر بكتير مستقل يستاهل مرحلة لوحده لو الأولوية طلبت كده.

## اختبار

9 اختبارات جديدة (إنشاء مسودة + حساب القيمة، الترحيل مع خصم مخزون وقيد محاسبي، idempotency الترحيل،
الإرجاع من دفعة محددة بالظبط + رفض لو الكمية أكبر من المتبقي، عزل الفروع، إلغاء مسودة مقابل رفض إلغاء
مُرحّل). الفل ريجريشن 489/489 على مرتين متتاليتين. الترحيل (migration 0008) اتأكد إنه idempotent
(تشغيلة تانية على قاعدة التطوير الحقيقية طبّقت صفر تغييرات). مفيش تحقق بمتصفح - مفيش واجهة مستخدم
للمرحلة دي كما هو موضّح فوق.
