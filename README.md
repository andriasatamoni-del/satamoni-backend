# Satamoni Backend (نقطة الانطلاق)

ده أول نسخة من الـ Backend المركزي اللي هيحل محل:
- `window.storage` في ملف الموقع (satamoni-ordering.jsx)
- اللصق اليدوي في شيتات "استيراد POS" و"استيراد كشف حساب" بالإكسل

## الشاشات الجاهزة

كل الصفحات دي في `public/` وبيتم تقديمها مباشرة من نفس السيرفر (`express.static`)، يعني رابط واحد وهيفتح كل حاجة. بتتصل بالـ API عن طريق نفس الأصل (`same-origin`) تلقائيًا — أو تقدر تحدد سيرفر تاني بتعريف `window.SATAMONI_API_URL` قبل تحميل الصفحة لو محتاج تفصل الفرونت عن الباك إند. كل واحدة ليها تسجيل دخول خاص بيها:

| الصفحة | لمين |
|---|---|
| `public/index.html` | الصفحة الرئيسية — روابط لكل الشاشات |
| `public/satamoni-pos.html` | الكاشير |
| `public/satamoni-admin.html` | الأدمن — إدارة الموظفين |
| `public/satamoni-menu.html` | الأدمن — المنيو، مناطق التوصيل، طرق الدفع |
| `public/satamoni-callcenter.html` | موظف الكول سنتر — بحث عملاء وتسجيل طلبات تليفونية |
| `public/satamoni-accounting.html` | أدمن/محاسب/مدير فرع — مصروفات، مشتريات، تقفيل كاش، كشف حساب المخزن |
| `public/satamoni-attendance.html` | كل الموظفين (حضور/انصراف) + أدمن/مدير فرع (شيفتات وسجل الحضور) |
| `public/satamoni-kitchen.html` | كل الفروع (طلب من السنتر كيتشن) + مدير السنتر كيتشن/أدمن (تنفيذ الطلبيات والتصنيع) |
| `satamoni-ordering.jsx` | موقع الطلب العام (بدون تسجيل دخول) — ده ملف React مصدري، محتاج build منفصل، مش متقدّم كـ static |

## التشغيل على جهازك أوفلاين (قبل ما ترفعه أونلاين)

### الطريقة الأسهل: Docker (تثبيت واحد بس، من غير Node أو Postgres منفصلين)

1. نزّل [Docker Desktop](https://www.docker.com/products/docker-desktop/) (مجاني، وندوز/ماك/لينكس) وشغّله.
2. نزّل الكود ده على جهازك (Clone من GitHub أو تحميل ZIP وفكه).
3. من داخل مجلد المشروع، شغّل:
   ```bash
   docker compose up --build
   ```
4. استنى شوية (أول مرة بتنزّل الصور وتبني الكود)، وبعدين افتح المتصفح على:
   **http://localhost:4000**
5. سجّل دخول بالحساب الافتراضي: `admin@satamoni.local` / `admin12345`
   (غيّرهم من `docker-compose.yml` قبل أي استخدام حقيقي، أو من شاشة إدارة المستخدمين بعد الدخول).

كل حاجة شغالة على جهازك بس، من غير إنترنت ومن غير أي حساب أونلاين. لما تقفل `docker compose up` (Ctrl+C) البيانات بتفضل محفوظة، وترجع تشتغل بنفس الأمر تاني.

للإيقاف والحذف الكامل (لو عايز تبدأ من الصفر): `docker compose down -v`

### الطريقة اليدوية (Node.js + PostgreSQL منفصلين)

محتاج Node.js وPostgreSQL متثبتين عندك:

```bash
npm install
cp .env.example .env      # عدّل DATABASE_URL و JWT_SECRET وبيانات أول أدمن
npm run ensure-schema      # بينشئ الجداول (لو مش موجودة) وحساب الأدمن في نفس الأمر
npm run dev                # تشغيل السيرفر محليًا للتجربة
```

بعد كده افتح `http://localhost:4000` في المتصفح — هتلاقي كل الشاشات شغالة من نفس السيرفر.

## لما تبقى جاهز — جرّبه أونلاين مجانًا (Render — من غير كارت ائتمان)

بعد ما تتأكد إن كل حاجة شغالة عندك أوفلاين، لو عايز رابط تشاركه أو تفتحه من موبايلك من غير ما جهازك يكون شغال:

1. اعمل حساب مجاني على [render.com](https://render.com) (بالإيميل أو GitHub، من غير كارت ائتمان).
2. اربط حساب Render بحساب GitHub بتاعك، وارفع الريبو ده لو لسه مش على GitHub.
3. من داشبورد Render: **New → Blueprint**، واختار الريبو ده. Render هيلاقي ملف `render.yaml` تلقائي ويجهزلك:
   - سيرفر ويب مجاني (`satamoni-backend`)
   - قاعدة بيانات Postgres مجانية (`satamoni-db`)
4. هيطلب منك تحدد `ADMIN_EMAIL` و`ADMIN_PASSWORD` (ده حساب الأدمن بتاعك — اختارهم إنت، منفصلين عن بيانات نسخة الـ Docker المحلية). اكتبهم واضغط **Apply**.
5. استنى 2-3 دقايق للديبلوي الأول. أول تشغيل بيعمل إنشاء الجداول تلقائيًا (`db/ensure-schema.js`).
6. هتاخد رابط زي `https://satamoni-backend-xxxx.onrender.com` — افتحه وهتلاقي صفحة فيها كل الشاشات، سجّل دخول بـ `ADMIN_EMAIL`/`ADMIN_PASSWORD` اللي حددتهم.

**ملاحظات عن الخطة المجانية:**
- السيرفر بينام بعد 15 دقيقة من غير استخدام، وأول طلب بعد النوم بياخد نص دقيقة تقريبًا يصحى (طبيعي، مش عطل).
- قاعدة البيانات المجانية عند Render بتتحذف تلقائيًا بعد 90 يوم — كويسة للتجربة، مش للاستخدام الفعلي طويل المدى.
- بعد ما تتأكد إن السيستم مناسب، تقدر تترقّى لخطة مدفوعة صغيرة على نفس الحساب من غير ما تعيد الإعداد من الأول.
- الفرع بتاع الكود دلوقتي هو `claude/restaurant-erp-system-jctgj5` مش `main` — لو Render سألك عن الـ branch وقت الإعداد، اختار الفرع ده.

(بديل: `npm run migrate` ثم `npm run seed:admin` لو عايز تتحكم في الخطوتين منفصلين.)

## الفرع يشتغل من غير نت + مزامنة تلقائية مع المركزي

الفكرة: كل فرع يشغّل نسخته المحلية بتاعته (Docker، زي فوق) على جهاز في الفرع نفسه — يعني البيع (POS) يفضل شغال 100% حتى لو النت اتقطع، لأن السيرفر وقاعدة البيانات جوه الفرع مش على الإنترنت. لما النت يرجع، سيرفيس مزامنة اختياري بيرفع المبيعات والمصروفات والمشتريات وتقفيل الكاش لسيرفر مركزي أونلاين (نسخة الـ Render) — عشان تقدر تشوف تقرير مجمّع لكل الفروع.

**إزاي تفعّلها (اختياري تمامًا، السيستم شغال عادي من غيرها):**

1. عندك نسخة مركزية شغالة أونلاين (Render) وعليها فروعك متسجلة من `satamoni-admin.html` أو `satamoni-menu.html`.
2. من صفحة الـ Environment بتاعة سيرفر Render، انسخ قيمة `SYNC_API_KEY` (Render بيولّدها تلقائي).
3. في جهاز الفرع، افتح `docker-compose.yml` واملأ قيم سيرفيس `sync`:
   ```yaml
   CENTRAL_SYNC_URL: "https://satamoni-backend-xxxx.onrender.com"
   SYNC_API_KEY: "القيمة اللي نسختها من Render"
   CENTRAL_BRANCH_ID: "3"   # رقم الفرع ده في النظام المركزي (مش رقمه المحلي)
   ```
4. شغّل: `docker compose up sync -d`

كل 5 دقايق (قابل للتعديل بـ `SYNC_INTERVAL_SECONDS`) بيحاول يرفع أي طلبات/مصروفات/مشتريات/تقفيلات كاش لسه ما اترفعتش. لو النت مقطوع أو المركزي مش راد، بيسجل المحاولة الفاشلة ويحاول تاني في الدورة الجاية من غير ما يوقف حاجة محليًا. كل عملية بتترفع مرة واحدة بس حتى لو اتبعتت مرتين (معمول لها هوية ثابتة `sync_uuid`)، فمفيش خطر تكرار بيانات.

**حدود النسخة الحالية (v1):** المزامنة بترفع الأرقام (المبيعات، المصروفات، المشتريات، تقفيل الكاش) للتقرير المركزي — مش لسه بتزامن المخزون أو كشف حساب الموردين أو ربط الطلب المزامَن بصنف/طريقة دفع معينة (النسخة المركزية للتقارير المجمّعة، مش لإعادة فتح الطلب من هناك).

## تسجيل الدخول والصلاحيات

النظام دلوقتي فيه Authentication كامل (JWT):

| الدور (role) | الصلاحيات |
|---|---|
| `admin` | كل حاجة، كل الفروع |
| `branch_manager` | تقارير وطلبات فرعه بس |
| `accountant` | التقارير المالية لكل الفروع (بدون إدارة فروع/مستخدمين) |
| `cashier` | تسجيل طلبات POS على فرعه بس |
| `callcenter` | تسجيل طلبات تليفونية (`source: "callcenter"`) لأي فرع/منطقة توصيل، وبحث بيانات العملاء |

- `POST /api/auth/login` — بريد إلكتروني + كلمة مرور، بترجع JWT صالح 12 ساعة.
- `GET /api/auth/me` — بيانات المستخدم المسجل دخوله (محتاج `Authorization: Bearer <token>`).
- شاشة الكاشير (`satamoni-pos.html`) بقت بتطلب تسجيل دخول قبل أي طلب، وبتقفل اختيار الفرع على فرع الكاشير نفسه (إلا لو أدمن).
- طلبات الموقع العامة (`source: "website"`) لسه من غير تسجيل دخول — العميل مش موظف.
- `satamoni-admin.html` — صفحة لإدارة الموظفين (أدمن بس): إضافة كاشير/مدير فرع/محاسب، تفعيل/تعطيل حساب.
- API الموظفين: `GET/POST /api/users` و`PATCH /api/users/:id` (أدمن بس).

## المنيو ومناطق التوصيل وطرق الدفع (بيانات حقيقية، من غير SQL)

`satamoni-menu.html` — شاشة أدمن بس لإدخال بيانات مطعمك الفعلية بنفسك (أقسام، أصناف، أحجام وأسعار، مناطق توصيل، طرق دفع) من غير أي دخول مباشر على قاعدة البيانات:

- `GET/POST /api/menu/categories` — أقسام المنيو
- `GET/POST /api/menu/items`، `PATCH /api/menu/items/:id` — الأصناف (اسم، وصف، تفعيل/تعطيل، "الأكثر طلبًا")
- `POST /api/menu/items/:id/variants`، `PATCH|DELETE /api/menu/variants/:id` — الأحجام والأسعار لكل صنف
- `GET/POST /api/config/delivery-areas`، `PATCH /api/config/delivery-areas/:id` — مناطق التوصيل ورسومها
- `GET/POST /api/config/payment-methods`، `PATCH /api/config/payment-methods/:id` — طرق الدفع وتفعيلها/تعطيلها

كل ده أدمن بس. أي حاجة تتضاف من هنا بتظهر فورًا في شاشة الكاشير والكول سنتر وموقع الطلب العام (بيقروا من نفس الـ `/api/config/full`).

### استيراد منيو حقيقي من إكسل دفعة واحدة

بدل ما تدخل مئات الأصناف واحد واحد من الشاشة، فيه سكريبت استيراد بيقرأ ملف JSON مُجهّز (اتعمل export له من شيت تكلفة المنيو) ويحط كل حاجة في قاعدة البيانات مرة واحدة: الأقسام، الأصناف، الأحجام والأسعار، **وريسبي كل صنف بالكامل** (كام جرام/قطعة من كل مكوّن) عشان خصم المخزون التلقائي يشتغل من أول يوم.

```bash
npm run import-menu          # بيقرأ db/seed-data/satamoni-menu.json افتراضيًا
# أو مع Docker:
docker compose exec app npm run import-menu
```

- آمن تشغيله أكتر من مرة (upsert بالاسم) — لو عدّلت الملف وشغّلته تاني، الأسعار والريسبي هيتحدّثوا ليطابقوا آخر نسخة من الملف.
- بيضيف كمان `unit_cost` (تكلفة الوحدة) لكل مكوّن في `inventory_items` — البيانات محفوظة للاستخدام في تحليل التكلفة لاحقًا، بس مفيش شاشة تقرير تكلفة/هامش ربح لسه (زي شيت "تحليل التكلفة والسعر" الأصلي).
- لو عايز تجهّز ملف JSON من إكسل تاني، الشكل المطلوب موجود في `db/seed-data/satamoni-menu.json` كمثال.

### تسعير مزدوج حسب مصدر الطلب (فرع مقابل طلبات)

بعض الأصناف بتتباع بسعر مختلف على تطبيق طلبات (بعد تغطية عمولته) عن سعر الفرع العادي. كل `menu_item_variant` بقى ليه عمود `talabat_price` منفصل (اختياري — `NULL` يعني الصنف مش مباع على طلبات حاليًا):

- `satamoni-menu.html` — لكل حجم/صنف فيه زرار "تعديل سعر طلبات" منفصل عن السعر العادي.
- `satamoni-pos.html` — فيه زرار قناة أعلى السلة: **"بيع الفرع"** (السعر العادي) أو **"طلبات 🛵"**. لما تختار "طلبات": المنيو بيتفلتر يعرض بس الأصناف اللي ليها سعر طلبات محدد، الأسعار المعروضة والمحسوبة في السلة بتبقى أسعار طلبات، وحقول الطاولة/التوصيل بتتخفي (لأن طلبات بتتولى التوصيل بنفسها). الطلب بيتسجل بـ `source: "talabat"` عشان يتفصل بسهولة في التقارير عن مبيعات الفرع العادية.
- `npm run import-talabat-prices` — بيحدّث `talabat_price` لمجموعة أصناف دفعة واحدة من `db/seed-data/talabat-prices.json` (نفس فكرة استيراد المنيو، آمن تكراره).
- خصم المخزون التلقائي (BOM) شغال بنفس الطريقة بغض النظر عن القناة — نفس الريسبي، السعر بس هو اللي بيختلف.

## المخازن الفعلية (Inventory / BOM)

- `inventory_items` — كتالوج المكونات الخام (دقيق، جبنة، ...) بوحدة القياس بتاعتها.
- `menu_item_variant_ingredients` — وصفة كل صنف (BOM): كام وحدة من كل مكوّن بتتاخد لما يتباع variant واحد.
- `branch_inventory_stock` — رصيد كل مكوّن في كل فرع لحظيًا.
- `inventory_movements` — سجل حركة المخزون بالكامل (بيع/توريد/تحويل/تسوية) لأي مراجعة لاحقًا.
- لما طلب POS يتسجل وله فرع، المخزون بينزل تلقائي حسب الوصفة (خصم في نفس الـ transaction بتاعة الطلب).
- API: `GET /api/inventory/items`, `POST /api/inventory/items` (أدمن أو مدير السنتر كيتشن)، `GET /api/inventory/stock?branchId=`، `POST /api/inventory/stock/adjust` (توريد/تحويل/تسوية يدوي)، `GET|PUT /api/inventory/recipe/:variantId`.

## السنتر كيتشن (خام → تصنيع → طلبيات فروع → تحويلات)

السنتر كيتشن هو صف في جدول `branches` عادي بس بعلامة `is_central_kitchen = true` (بتتحدد وقت إنشاء الفرع من `satamoni-admin.html`، وفيها كمان قسم "الفروع" جديد لإنشاء الفروع نفسها لأول مرة). موظف مربوط بالفرع ده (`branch_manager` غالبًا) بياخد صلاحيات السنتر كيتشن تلقائيًا — مفيش دور خاص منفصل، الصلاحية بتتحدد من فرعه.

- **كل مكوّن في الكتالوج بقى له نوع** (`item_type`): `raw` (بيتشترى من مورد) أو `manufactured` (بيتعمل في السنتر كيتشن من مكونات تانية).
- **وصفة تصنيع** (`manufacturing_recipe_items`) — تمامًا زي وصفة المنيو (BOM) بس هنا الناتج مكوّن مصنّع مش صنف مبيع، والمدخلات ممكن تكون خام أو مصنّعة هي كمان (تصنيع متعدد المراحل لو احتجت).
- **`POST /api/inventory/produce`** — تسجيل عملية تصنيع فعلية: بتاخد وصفة الصنف المصنّع، تخصم المكونات الداخلة من مخزون السنتر كيتشن، وتزود رصيد الصنف المصنّع — كله في transaction واحدة.
- **طلبية فرع** (`kitchen_orders` + `kitchen_order_items`, `POST/GET /api/kitchen-orders`) — أي فرع يطلب أصناف (خام أو مصنّعة) من السنتر كيتشن.
- **تنفيذ الطلبية / تحويل** (`POST /api/kitchen-transfers/itemized`) — السنتر كيتشن يشوف الطلبيات المعلّقة، يحدد الكميات الفعلية اللي هيبعتها (ممكن تختلف عن المطلوب)، والتحويل بينزل من مخزون السنتر كيتشن ويزود مخزون الفرع المستقبِل تلقائيًا، ويقفل الطلبية "اتنفذت". تكلفة التحويل (`amount_at_cost`) بتتحسب تلقائي من `unit_cost` بتاع كل مكوّن.
- `satamoni-kitchen.html` — شاشة واحدة بثلاث تبويبات: "اطلب من السنتر كيتشن" (كل الفروع)، و"تنفيذ الطلبيات" و"التصنيع" (السنتر كيتشن/الأدمن بس، بتظهر تلقائي حسب فرع المستخدم).

## المصروفات / المشتريات / الموردين / تقفيل الكاش

بديل كامل للإدخال اليدوي بالإكسل، بنفس الجداول اللي كانت موجودة بس دلوقتي ليها API:

| Endpoint | مين يقدر يستخدمه |
|---|---|
| `GET/POST /api/expenses` | أدمن، محاسب، مدير فرع (على فرعه بس) |
| `GET/POST /api/purchases` | أدمن، محاسب، مدير فرع (على فرعه بس) |
| `GET /api/kitchen-transfers` | أدمن، محاسب، مدير فرع (فرعه بس) |
| `POST /api/kitchen-transfers` | أدمن بس (سنتر كيتشن بيبعت بضاعة بالتكلفة لفرع) |
| `GET/POST /api/suppliers/ledger` | القراءة: أدمن/محاسب/مدير فرع (فرعه) — الإضافة: أدمن ومحاسب بس |
| `GET/POST /api/cash-sessions` | أدمن، محاسب، مدير فرع، كاشير (على فرعه) — ده تقفيل الكاش اليومي |

`POST /api/cash-sessions` بيعمل upsert بمفتاح (فرع + تاريخ)، ويحسب `expected_closing_cash` و`cash_difference` جوه السيرفر (مش بإدخال يدوي) عشان محدش يغلط في المعادلة. البيانات دي هي اللي بتغذي `/api/reports/daily` (شيت "لوحة التحكم").

`satamoni-accounting.html` — شاشة واحدة بأربع تبويبات (مصروفات / مشتريات / تقفيل كاش / كشف حساب المخزن)، مقفولة على فرع مدير الفرع تلقائيًا، وإضافة كشف الحساب معطّلة في الواجهة لغير الأدمن/المحاسب (بما يطابق صلاحيات الـ API).

## العملاء (CRM) وكول سنتر

- كل طلب فيه رقم موبايل (POS/موقع/كول سنتر) بيعمل upsert تلقائي في جدول `customers` — من غير أي إدخال يدوي إضافي.
- `GET /api/customers?phone=` — بروفايل عميل كامل: بياناته + عدد طلباته + إجمالي إنفاقه + آخر 20 طلب (ده اللي موظف الكول سنتر بيشوفه وقت الرنة).
- `GET /api/customers?q=` — بحث بالاسم أو رقم التليفون.
- `PATCH /api/customers/:phone` — تسجيل ملاحظات (عنوان مفضل، شكوى سابقة) أو نقاط ولاء.
- `POST /api/orders` بـ `source: "callcenter"` — موظف الكول سنتر (أو الأدمن) بس، ومش مقفول على فرع واحد زي الكاشير (لأنه بياخد طلبات لكل الفروع/مناطق التوصيل).
- `satamoni-callcenter.html` — شاشة كاملة: بحث عن العميل (يظهر عدد طلباته وإجمالي إنفاقه وآخر 20 طلب وملاحظاته)، وتسجيل طلب جديد (دليفري/تيك أواي/صالة) بنفس منطق شاشة الكاشير.

## الموارد البشرية (Shifts + Attendance)

- `GET/POST /api/hr/shifts` — جدولة شيفتات الموظفين (الإضافة: أدمن أو مدير الفرع لفرعه بس).
- `POST /api/hr/attendance/clock-in` و`clock-out` — كل موظف بيسجل حضوره/انصرافه بنفسه بالتوكن بتاعه؛ فيه حماية من تسجيل حضور مزدوج أو انصراف من غير حضور مفتوح.
- `GET /api/hr/attendance` — سجل الحضور الكامل (أدمن أو مدير الفرع لفرعه).
- `GET /api/users?branchId=` بقى متاح لمدير الفرع كمان (مقفول على فرعه)، مش أدمن بس، عشان يقدر يشوف موظفينه ويعيّنلهم شيفتات.
- `satamoni-attendance.html` — أي موظف بيسجل حضوره/انصرافه بنفسه، وأدمن/مدير الفرع كمان يشوفوا تعيين الشيفتات وسجل الحضور الكامل لفرعهم.

## الجداول وربطها بالإكسل الحالي

| جدول | بديل لأي شيت في الإكسل |
|---|---|
| `branches` | صف الفروع + سنتر كيتشن |
| `daily_cash_sessions` | شيت "فرع محرم بك/الإبراهيمية/العصافرة" (المبيعات والكاش) |
| `expenses` | أعمدة المصروفات في نفس الشيتات |
| `purchases` / `kitchen_transfers` | المشتريات والتحويلات من سنتر كيتشن |
| `supplier_ledger_entries` | شيت "استيراد كشف حساب" لكل فرع |
| `orders` / `order_items` | طلبات الموقع (بديل window.storage) |
| `users` | تسجيل الدخول والصلاحيات (أدمن/مدير فرع/محاسب/كاشير/كول سنتر) |
| `inventory_items` / `branch_inventory_stock` / `menu_item_variant_ingredients` / `inventory_movements` | المخزون الفعلي ووصفات الأصناف (بديل الجرد اليدوي) |
| `customers` | سجل CRM للعملاء (بديل معرفة العميل من ذاكرة الموظف وقت المكالمة) |
| `shifts` / `attendance_records` | جدولة الشيفتات والحضور والانصراف |
| `v_daily_branch_summary` (view) | شيت "لوحة التحكم" |
| `v_customer_order_stats` (view) | عدد طلبات كل عميل وإجمالي إنفاقه |

## ملاحظة مهمة

النسخة دي لسه MVP، وخطة Render المجانية معمولة للتجربة بس. قبل أي استخدام فعلي في الإنتاج (بيانات حقيقية وعملاء حقيقيين)، لازم كمان نضيف/نراجع:
- ترقية لخطة مدفوعة (السيرفر المجاني بينام، والداتابيز المجانية بتتحذف بعد 90 يوم)
- نسخ احتياطي دوري لقاعدة البيانات
- Rate limiting على `/api/auth/login` عشان يمنع محاولات تخمين الباسورد
- مراجعة أمان قبل فتحه لعملاء حقيقيين (HTTPS متوفر تلقائي على Render)
