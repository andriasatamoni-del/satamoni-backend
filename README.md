# Satamoni Backend (نقطة الانطلاق)

ده أول نسخة من الـ Backend المركزي اللي هيحل محل:
- `window.storage` في ملف الموقع (satamoni-ordering.jsx)
- اللصق اليدوي في شيتات "استيراد POS" و"استيراد كشف حساب" بالإكسل

## الشاشات الجاهزة

كل الصفحات دي في `public/` وبيتم تقديمها مباشرة من نفس السيرفر (`express.static`)، يعني رابط واحد وهيفتح كل حاجة. بتتصل بالـ API عن طريق نفس الأصل (`same-origin`) تلقائيًا — أو تقدر تحدد سيرفر تاني بتعريف `window.SATAMONI_API_URL` قبل تحميل الصفحة لو محتاج تفصل الفرونت عن الباك إند. كل واحدة ليها تسجيل دخول خاص بيها:

| الصفحة | لمين |
|---|---|
| `public/index.html` | الصفحة الرئيسية — روابط لكل الشاشات |
| `public/satamoni-pos.html` | الكاشير |
| `public/satamoni-admin.html` | الأدمن — إدارة الموظفين |
| `public/satamoni-menu.html` | الأدمن — المنيو، مناطق التوصيل، طرق الدفع، العروض/الكومبوهات |
| `public/satamoni-callcenter.html` | موظف الكول سنتر — بحث عملاء وتسجيل طلبات تليفونية |
| `public/satamoni-delivery.html` | كاشير/مدير فرع/كول سنتر/محاسب/أدمن — دورة حياة طلبات الدليفري (تحت التحضير/في الطريق/تحصيل) وتذكرة المطبخ |
| `public/satamoni-accounting.html` | أدمن/محاسب/مدير فرع — مصروفات، مشتريات، تقفيل كاش، كشف حساب المخزن، تحليل التكلفة، قائمة الدخل |
| `public/satamoni-attendance.html` | كل الموظفين (حضور/انصراف) + أدمن/مدير فرع (شيفتات وسجل الحضور) |
| `public/satamoni-kitchen.html` | كل الفروع (طلب من السنتر كيتشن) + مدير السنتر كيتشن/أدمن (تنفيذ الطلبيات، التصنيع، جرد المخزون، تسجيل الهالك) |
| `public/satamoni-payroll.html` | أدمن/محاسب — الرواتب: الموظفين، استيراد وتصحيح البصمة، حضور المطبخ المركزي، سلف وجزاءات ومكافآت، الملخص المحسوب |
| `public/satamoni-dashboard.html` | أدمن/محاسب — داش بورد المالك: كل تفاصيل الشغل في شاشة واحدة مع رسوم بيانية |
| `public/satamoni-reports.html` | أدمن/محاسب/مدير فرع — مركز التقارير: كل تقارير المبيعات والمخزون والتشغيل في شاشة واحدة (تفاصيل تحت) |
| `satamoni-ordering.jsx` | موقع الطلب العام (بدون تسجيل دخول) — ده ملف React مصدري، محتاج build منفصل، مش متقدّم كـ static |

## التشغيل على جهازك أوفلاين (قبل ما ترفعه أونلاين)

### الطريقة الأسهل: Docker (تثبيت واحد بس، من غير Node أو Postgres منفصلين)

1. نزّل [Docker Desktop](https://www.docker.com/products/docker-desktop/) (مجاني، وندوز/ماك/لينكس) وشغّله.
2. نزّل الكود ده على جهازك (Clone من GitHub أو تحميل ZIP وفكه).
3. من داخل مجلد المشروع، شغّل:
   ```bash
   docker compose up --build
   ```
4. استنى شوية (أول مرة بتنزّل الصور وتبني الكود)، وبعدين افتح المتصفح على:
   **http://localhost:4000**
5. سجّل دخول بالحساب الافتراضي: `admin@satamoni.local` / `admin12345`
   (غيّرهم من `docker-compose.yml` قبل أي استخدام حقيقي، أو من شاشة إدارة المستخدمين بعد الدخول).

كل حاجة شغالة على جهازك بس، من غير إنترنت ومن غير أي حساب أونلاين. لما تقفل `docker compose up` (Ctrl+C) البيانات بتفضل محفوظة، وترجع تشتغل بنفس الأمر تاني.

للإيقاف والحذف الكامل (لو عايز تبدأ من الصفر): `docker compose down -v`

### الطريقة اليدوية (Node.js + PostgreSQL منفصلين)

محتاج Node.js وPostgreSQL متثبتين عندك:

```bash
npm install
cp .env.example .env      # عدّل DATABASE_URL و JWT_SECRET وبيانات أول أدمن
npm run ensure-schema      # بينشئ الجداول (لو مش موجودة) وحساب الأدمن في نفس الأمر
npm run dev                # تشغيل السيرفر محليًا للتجربة
```

بعد كده افتح `http://localhost:4000` في المتصفح — هتلاقي كل الشاشات شغالة من نفس السيرفر.

## لما تبقى جاهز — جرّبه أونلاين مجانًا (Render — من غير كارت ائتمان)

بعد ما تتأكد إن كل حاجة شغالة عندك أوفلاين، لو عايز رابط تشاركه أو تفتحه من موبايلك من غير ما جهازك يكون شغال:

1. اعمل حساب مجاني على [render.com](https://render.com) (بالإيميل أو GitHub، من غير كارت ائتمان).
2. اربط حساب Render بحساب GitHub بتاعك، وارفع الريبو ده لو لسه مش على GitHub.
3. من داشبورد Render: **New → Blueprint**، واختار الريبو ده. Render هيلاقي ملف `render.yaml` تلقائي ويجهزلك:
   - سيرفر ويب مجاني (`satamoni-backend`)
   - قاعدة بيانات Postgres مجانية (`satamoni-db`)
4. هيطلب منك تحدد `ADMIN_EMAIL` و`ADMIN_PASSWORD` (ده حساب الأدمن بتاعك — اختارهم إنت، منفصلين عن بيانات نسخة الـ Docker المحلية). اكتبهم واضغط **Apply**.
5. استنى 2-3 دقايق للديبلوي الأول. أول تشغيل بيعمل إنشاء الجداول تلقائيًا (`db/ensure-schema.js`).
6. هتاخد رابط زي `https://satamoni-backend-xxxx.onrender.com` — افتحه وهتلاقي صفحة فيها كل الشاشات، سجّل دخول بـ `ADMIN_EMAIL`/`ADMIN_PASSWORD` اللي حددتهم.

**ملاحظات عن الخطة المجانية:**
- السيرفر بينام بعد 15 دقيقة من غير استخدام، وأول طلب بعد النوم بياخد نص دقيقة تقريبًا يصحى (طبيعي، مش عطل).
- قاعدة البيانات المجانية عند Render بتتحذف تلقائيًا بعد 90 يوم — كويسة للتجربة، مش للاستخدام الفعلي طويل المدى.
- بعد ما تتأكد إن السيستم مناسب، تقدر تترقّى لخطة مدفوعة صغيرة على نفس الحساب من غير ما تعيد الإعداد من الأول.
- الفرع بتاع الكود دلوقتي هو `claude/restaurant-erp-system-jctgj5` مش `main` — لو Render سألك عن الـ branch وقت الإعداد، اختار الفرع ده.

(بديل: `npm run migrate` ثم `npm run seed:admin` لو عايز تتحكم في الخطوتين منفصلين.)

## الفرع يشتغل من غير نت + مزامنة تلقائية مع المركزي

الفكرة: كل فرع يشغّل نسخته المحلية بتاعته (Docker، زي فوق) على جهاز في الفرع نفسه — يعني البيع (POS) يفضل شغال 100% حتى لو النت اتقطع، لأن السيرفر وقاعدة البيانات جوه الفرع مش على الإنترنت. لما النت يرجع، سيرفيس مزامنة اختياري بيرفع المبيعات والمصروفات والمشتريات وتقفيل الكاش لسيرفر مركزي أونلاين (نسخة الـ Render) — عشان تقدر تشوف تقرير مجمّع لكل الفروع.

**إزاي تفعّلها (اختياري تمامًا، السيستم شغال عادي من غيرها):**

1. عندك نسخة مركزية شغالة أونلاين (Render) وعليها فروعك متسجلة من `satamoni-admin.html` أو `satamoni-menu.html`.
2. من صفحة الـ Environment بتاعة سيرفر Render، انسخ قيمة `SYNC_API_KEY` (Render بيولّدها تلقائي).
3. في جهاز الفرع، افتح `docker-compose.yml` واملأ قيم سيرفيس `sync`:
   ```yaml
   CENTRAL_SYNC_URL: "https://satamoni-backend-xxxx.onrender.com"
   SYNC_API_KEY: "القيمة اللي نسختها من Render"
   CENTRAL_BRANCH_ID: "3"   # رقم الفرع ده في النظام المركزي (مش رقمه المحلي)
   ```
4. شغّل: `docker compose up sync -d`

كل 5 دقايق (قابل للتعديل بـ `SYNC_INTERVAL_SECONDS`) بيحاول يرفع أي طلبات/مصروفات/مشتريات/تقفيلات كاش لسه ما اترفعتش. لو النت مقطوع أو المركزي مش راد، بيسجل المحاولة الفاشلة ويحاول تاني في الدورة الجاية من غير ما يوقف حاجة محليًا. كل عملية بتترفع مرة واحدة بس حتى لو اتبعتت مرتين (معمول لها هوية ثابتة `sync_uuid`)، فمفيش خطر تكرار بيانات.

**التقرير المركزي شامل التكلفة والربحية مش الإيرادات بس:** كل سطر صنف في الطلب المُزامَن بيحمل معاه `cost_at_sale` (تكلفة الريسبي وقت البيع، نفس القيمة المجمّدة محليًا) — فتقارير قائمة الدخل وداش بورد المالك على السيرفر المركزي بتحسب هامش الربح والتكلفة صح لكل الفروع مجمّعة، مش الإيرادات بس، من غير أي كود إضافي (نفس دوال الحساب بالظبط).

**التعديلات اللي بتحصل بعد أول مزامنة بتترفع تاني:** لو طلب اتسترجع (Void) أو اتغيّرت حالة تحصيله بعد ما كان اتبعت للمركزي أصلًا، السيستم بيسجّل إنه "لسه محتاج مزامنة" تلقائيًا (`synced_at` بيترجع فاضي) فالدورة الجاية بترفع الحالة الجديدة وتحدّث نسخة المركزي — عشان تقرير الإيرادات المجمّع متفضلش شايل بيع اتلغى فعليًا في الفرع.

**بند المصروف بيتراجع بالاسم مش بالرقم:** لأن ترقيم بنود المصروفات (`expense_categories`) محلي لكل فرع ومختلف عن المركزي، المزامنة بتبعت اسم البند، والمركزي بيدوّر على بند بنفس الاسم أو ينشئه لو مش موجود (نفس البنود الافتراضية موجودة في التثبيت الأول عادةً، فبيتلاقوا تلقائي).

**حدود النسخة الحالية:** الإيرادات/التكلفة/المصروفات مجمّعة صح، لكن لسه مفيش مزامنة للمخزون أو كشف حساب الموردين أو تفاصيل الصنف نفسه (item_id/variant_id) المُباع — لأن ترقيم المنيو محلي لكل فرع ومختلف عن المركزي، فالنسخة المركزية بتعرف "اتباع بكام وتكلفته كام" مش "بيتزا بسطرمة حجم وسط" بالتحديد. النسخة المركزية للتقارير المجمّعة (أرقام)، مش لإعادة فتح الطلب من هناك.

## تسجيل الدخول والصلاحيات

النظام دلوقتي فيه Authentication كامل (JWT):

| الدور (role) | الصلاحيات |
|---|---|
| `admin` | كل حاجة، كل الفروع |
| `branch_manager` | تقارير وطلبات فرعه بس |
| `accountant` | التقارير المالية لكل الفروع (بدون إدارة فروع/مستخدمين) |
| `cashier` | تسجيل طلبات POS على فرعه بس |
| `callcenter` | تسجيل طلبات تليفونية (`source: "callcenter"`) لأي فرع/منطقة توصيل، وبحث بيانات العملاء |

- `POST /api/auth/login` — بريد إلكتروني + كلمة مرور، بترجع JWT صالح 12 ساعة.
- `GET /api/auth/me` — بيانات المستخدم المسجل دخوله (محتاج `Authorization: Bearer <token>`).
- شاشة الكاشير (`satamoni-pos.html`) بقت بتطلب تسجيل دخول قبل أي طلب، وبتقفل اختيار الفرع على فرع الكاشير نفسه (إلا لو أدمن).
- طلبات الموقع العامة (`source: "website"`) لسه من غير تسجيل دخول — العميل مش موظف.
- `satamoni-admin.html` — صفحة لإدارة الموظفين (أدمن بس): إضافة كاشير/مدير فرع/محاسب، تفعيل/تعطيل حساب.
- API الموظفين: `GET/POST /api/users` و`PATCH /api/users/:id` (أدمن بس).

## المنيو ومناطق التوصيل وطرق الدفع (بيانات حقيقية، من غير SQL)

`satamoni-menu.html` — شاشة أدمن بس لإدخال بيانات مطعمك الفعلية بنفسك (أقسام، أصناف، أحجام وأسعار، مناطق توصيل، طرق دفع) من غير أي دخول مباشر على قاعدة البيانات:

- `GET/POST /api/menu/categories`، `PATCH /api/menu/categories/:id` — أقسام المنيو، بترتيب ظهور (`displayOrder`) ومجموعة (`menuGroup`: منيو عادي أو منيو صيامي منفصل).
- `GET/POST /api/menu/items`، `PATCH /api/menu/items/:id` — الأصناف (اسم، وصف، تفعيل/تعطيل، "الأكثر طلبًا")
- `POST /api/menu/items/:id/variants`، `PATCH|DELETE /api/menu/variants/:id` — الأحجام والأسعار لكل صنف
- `GET/POST /api/menu/items/:id/modifiers`، `PATCH|DELETE /api/menu/modifiers/:id` — مرفقات/توصيفات الصنف (إضافة موتزريلا، بدون طماطم...) بسعر زيادة أو مجانًا.
- `GET/PUT /api/inventory/recipe/:variantId` — كارتة الصنف (الريسبي): كل مكوّن وكميته لكل وحدة مباعة، معروضة وقابلة للتعديل من `satamoni-menu.html` مباشرة تحت كل حجم.
- `GET/POST /api/config/delivery-areas`، `PATCH /api/config/delivery-areas/:id` — مناطق التوصيل ورسومها
- `GET/POST /api/config/payment-methods`، `PATCH /api/config/payment-methods/:id` — طرق الدفع، تفعيلها/تعطيلها، ونوعها (`kind`: كاش/فيزا-محفظة/آجل).

كل ده أدمن بس. أي حاجة تتضاف من هنا بتظهر فورًا في شاشة الكاشير والكول سنتر وموقع الطلب العام (بيقروا من نفس الـ `/api/config/full`).

### الأحجام والمرفقات في شاشة البيع

لما تدوس على صنف له أكتر من حجم أو له مرفقات متاحة، بتفتح نافذة اختيار (بدل الـ prompt القديم): تختار الحجم (وسط/كبير...) وتأشّر على أي مرفقات عايزها (إضافة موتزريلا، بدون طماطم...)، والسعر الإجمالي بيتحدث لحظيًا. المرفقات المختارة بتتسجل في السلة وفي الطلب، وبتتحفظ باسمها وسعرها وقت البيع (`order_item_modifiers`) عشان لو سعر المرفق اتغيّر بعدين الطلبات القديمة تفضل دقيقة.

**سعر المرفق ممكن يختلف حسب الحجم** — مثلاً "اضافة سدق" سعرها على بيتزا وسط مختلف عن فطير كبير. `menu_item_modifiers.price_delta` هو السعر الافتراضي، وجدول منفصل `menu_item_modifier_variant_prices` بيحفظ سعر مخصوص لأي (مرفق، حجم) محتاج سعر مختلف عن الافتراضي — لو الحجم مالوش سعر مخصوص، بيرجع تلقائي للسعر الافتراضي. السيرفر (`resolveOrderItems` في `routes/orders.js`) بيحسم السعر الصح وقت الطلب حسب الحجم المختار فعليًا (مش بيصدّق سعر الواجهة، زي باقي أسعار المنيو). شاشة إدارة المنيو (`satamoni-menu.html`) بتوضح تحت كل مرفق سعره لكل حجم (★ يعني سعر مخصوص مش الافتراضي)، وممكن تعدّله بضغطة.

### منيو عادي ومنيو صيامي منفصلين

لو فيه أقسام موزّعة على مجموعتين مختلفتين (`menuGroup`)، بيظهر تلقائيًا زرار تبديل أعلى المنيو في `satamoni-pos.html` و`satamoni-callcenter.html` — "المنيو العادي" / "المنيو الصيامي" — وبيتفلتر الأقسام والأصناف على حسبه. لو كل الأقسام في مجموعة واحدة، الزرار بيختفي تلقائيًا (مفيش داعي له). ترتيب ظهور الأقسام (`displayOrder`) قابل للتعديل من نفس شاشة إدارة المنيو.

### استيراد منيو حقيقي من إكسل دفعة واحدة

بدل ما تدخل مئات الأصناف واحد واحد من الشاشة، فيه سكريبت استيراد بيقرأ ملف JSON مُجهّز (اتعمل export له من شيت تكلفة المنيو) ويحط كل حاجة في قاعدة البيانات مرة واحدة: الأقسام، الأصناف، الأحجام والأسعار، **وريسبي كل صنف بالكامل** (كام جرام/قطعة من كل مكوّن) عشان خصم المخزون التلقائي يشتغل من أول يوم.

```bash
npm run import-menu          # بيقرأ db/seed-data/satamoni-menu.json افتراضيًا
# أو مع Docker:
docker compose exec app npm run import-menu
```

- آمن تشغيله أكتر من مرة (upsert بالاسم) — لو عدّلت الملف وشغّلته تاني، الأسعار والريسبي هيتحدّثوا ليطابقوا آخر نسخة من الملف.
- بيضيف كمان `unit_cost` (تكلفة الوحدة) لكل مكوّن في `inventory_items` — البيانات محفوظة للاستخدام في تحليل التكلفة لاحقًا، بس مفيش شاشة تقرير تكلفة/هامش ربح لسه (زي شيت "تحليل التكلفة والسعر" الأصلي).
- لو عايز تجهّز ملف JSON من إكسل تاني، الشكل المطلوب موجود في `db/seed-data/satamoni-menu.json` كمثال.
- **مهم:** كل صنف بحجمين لازم يتسجل **صنف واحد** بقايمة `variants` فيها الحجمين (كل حجم بريسبيه وسعره الخاص) — مش صنفين منفصلين بنفس الاسم زي "بيتزا مارجريتا وسط" و"بيتزا مارجريتا حجم اكبر". لو اتسجلوا منفصلين، شاشة البيع هتعرضهم كصنفين لوحدهم بدل صنف واحد بيختار منه الحجم.
- **الإضافات المشتركة** (اضافة سدق/بسطرمة/جبنة...) بتتسجل في مفتاح `modifiers` منفصل جوه نفس الملف، مش كأصناف عادية: كل عنصر فيه `name`، وإما `targetItem` (اسم صنف واحد بعينه) أو `targetCategories` (كل أصناف قسم/أقسام معينة، زي "كل البيتزا")، و`defaultPrice` (السعر الافتراضي)، و`variantPrices` (سعر مخصوص لحجم بعينه لو مختلف عن الافتراضي). السكريبت بيربطها تلقائيًا كمرفقات (`menu_item_modifiers`) على كل الأصناف المستهدَفة وقت الاستيراد.

### تسعير مزدوج حسب مصدر الطلب (فرع مقابل طلبات)

بعض الأصناف بتتباع بسعر مختلف على تطبيق طلبات (بعد تغطية عمولته) عن سعر الفرع العادي. كل `menu_item_variant` بقى ليه عمود `talabat_price` منفصل (اختياري — `NULL` يعني الصنف مش مباع على طلبات حاليًا):

- `satamoni-menu.html` — لكل حجم/صنف فيه زرار "تعديل سعر طلبات" منفصل عن السعر العادي.
- `satamoni-pos.html` — فيه زرار قناة أعلى السلة: **"بيع الفرع"** (السعر العادي) أو **"طلبات 🛵"**. لما تختار "طلبات": المنيو بيتفلتر يعرض بس الأصناف اللي ليها سعر طلبات محدد، الأسعار المعروضة والمحسوبة في السلة بتبقى أسعار طلبات، وحقول الطاولة/التوصيل بتتخفي (لأن طلبات بتتولى التوصيل بنفسها). الطلب بيتسجل بـ `source: "talabat"` عشان يتفصل بسهولة في التقارير عن مبيعات الفرع العادية.
- `npm run import-talabat-prices` — بيحدّث `talabat_price` لمجموعة أصناف دفعة واحدة من `db/seed-data/talabat-prices.json` (نفس فكرة استيراد المنيو، آمن تكراره). كل صف فيه `[اسم الصنف, اسم الحجم, سعر طلبات]` — لازم يطابقوا الاسم والحجم بالظبط زي ما اتسجلوا في `satamoni-menu.json`.
- خصم المخزون التلقائي (BOM) شغال بنفس الطريقة بغض النظر عن القناة — نفس الريسبي، السعر بس هو اللي بيختلف.

## العروض والكومبوهات

عرض بسعر واحد بيجمّع أكتر من صنف/حجم مع بعض (زي "كومبو ٢ بيتزا")، من غير ما تحتاج تعمله صنف منيو منفصل بريسبي مكرر:

- `combos` + `combo_items` — اسم العرض وسعره، وقائمة الأصناف (variant + كمية) اللي بتتكوّن منها.
- `order_items.combo_id` — سطر الطلب لو بيمثّل عرض بيتسجل بيه بس (`item_id`/`variant_id` بيفضلوا `NULL`)، مش بالأصناف المفردة.
- **خصم المخزون**: العرض مالوش وصفة مباشرة — وقت البيع بيتفكّ لأصنافه الأصلية، وكل صنف بياخد وصفته العادية (BOM) مضروبة في كميته جوه العرض × عدد العروض المباعة، بنفس دقة الأرقام العشرية (`::numeric` في SQL).
- API: `GET /api/combos` (العروض النشطة بس — للبيع)، `GET /api/combos/all` (كل العروض شاملة المعطّلة — أدمن)، `POST /api/combos`، `PATCH /api/combos/:id` (اسم/سعر/تفعيل)، `PUT /api/combos/:id/items` (تعديل قائمة الأصناف) — كلها أدمن بس.
- `satamoni-menu.html` — تبويب "العروض": إضافة عرض جديد باختيار أصناف وكمياتها، تفعيل/تعطيل، وتعديل قائمة الأصناف لأي عرض موجود.
- `satamoni-pos.html` — العروض النشطة بتظهر كقسم "🎁 العروض" في شاشة الكاشير (قناة بيع الفرع بس، مالهاش سعر طلبات منفصل)، وبتتضاف للسلة زي أي صنف عادي.

## المخازن الفعلية (Inventory / BOM)

- `inventory_items` — كتالوج المكونات الخام (دقيق، جبنة، ...) بوحدة القياس بتاعتها.
- `menu_item_variant_ingredients` — وصفة كل صنف (BOM): كام وحدة من كل مكوّن بتتاخد لما يتباع variant واحد.
- `branch_inventory_stock` — رصيد كل مكوّن في كل فرع لحظيًا.
- `inventory_movements` — سجل حركة المخزون بالكامل (بيع/توريد/تحويل/تسوية) لأي مراجعة لاحقًا.
- لما طلب POS يتسجل وله فرع، المخزون بينزل تلقائي حسب الوصفة (خصم في نفس الـ transaction بتاعة الطلب).
- API: `GET /api/inventory/items`, `POST /api/inventory/items` (أدمن أو مدير السنتر كيتشن)، `GET /api/inventory/stock?branchId=`، `POST /api/inventory/stock/adjust` (توريد/تحويل/تسوية يدوي)، `GET|PUT /api/inventory/recipe/:variantId`.

### جرد المخزون (تسوية الرصيد الفعلي)

بديل شيت الجرد اليدوي — بدل ما تحسب الفرق بإيدك وتعمل قيد تسوية يدوي، بتدخّل الكمية الفعلية بعد العد وكل حاجة بتتحسب وتتسجل تلقائيًا:

- **`POST /api/inventory/reconcile`** — بياخد `{branchId, inventoryItemId, actualQuantity, notes}`، يقارن بالرصيد الحالي في `branch_inventory_stock`، يحسب الفرق (`variance`)، يحدّث الرصيد لنفس القيمة الفعلية، ويسجل حركة `adjustment` في `inventory_movements` فيها الفرق ومذكرة توضح "كان X، الفعلي Y" (أدمن أو مدير فرع، على فرعه بس).
- `satamoni-kitchen.html` — تبويب جديد "جرد المخزون" (أدمن/مدير فرع بس): جدول بكل الأصناف ورصيدها الحالي، خانة تدخّل فيها العدد الفعلي، وزرار تحديث لكل صف يعرض الفرق فورًا. الأدمن بيختار الفرع من قائمة منسدلة (بيشمل السنتر كيتشن)، ومدير الفرع مقفول على فرعه تلقائيًا.

### تسجيل الهالك (تلف / انتهاء صلاحية / كسر)

- **`POST /api/inventory/waste`** — بياخد `{branchId, inventoryItemId, quantity, reason, businessDate}`، بيخصم الكمية من `branch_inventory_stock` وبيسجل حركة `inventory_movements` بنوع `waste` منفصلة عن أي بيع أو تسوية (أدمن أو مدير فرع، على فرعه بس).
- `satamoni-kitchen.html` — تبويب "تسجيل هالك" (أدمن/مدير فرع بس): فورم بسيط (صنف/كمية/تاريخ/سبب) + جدول بآخر عمليات الهالك المسجّلة للفرع في الشهر الحالي.
- التقرير الكامل (قيمة الهالك حسب الصنف + كل العمليات) متاح في مركز التقارير (`GET /api/reports/waste`، تحت).

## السنتر كيتشن (خام → تصنيع → طلبيات فروع → تحويلات)

السنتر كيتشن هو صف في جدول `branches` عادي بس بعلامة `is_central_kitchen = true` (بتتحدد وقت إنشاء الفرع من `satamoni-admin.html`، وفيها كمان قسم "الفروع" جديد لإنشاء الفروع نفسها لأول مرة). موظف مربوط بالفرع ده (`branch_manager` غالبًا) بياخد صلاحيات السنتر كيتشن تلقائيًا — مفيش دور خاص منفصل، الصلاحية بتتحدد من فرعه.

- **كل مكوّن في الكتالوج بقى له نوع** (`item_type`): `raw` (بيتشترى من مورد) أو `manufactured` (بيتعمل في السنتر كيتشن من مكونات تانية).
- **وصفة تصنيع** (`manufacturing_recipe_items`) — تمامًا زي وصفة المنيو (BOM) بس هنا الناتج مكوّن مصنّع مش صنف مبيع، والمدخلات ممكن تكون خام أو مصنّعة هي كمان (تصنيع متعدد المراحل لو احتجت).
- **`POST /api/inventory/produce`** — تسجيل عملية تصنيع فعلية: بتاخد وصفة الصنف المصنّع، تخصم المكونات الداخلة من مخزون السنتر كيتشن، وتزود رصيد الصنف المصنّع — كله في transaction واحدة.
- **طلبية فرع** (`kitchen_orders` + `kitchen_order_items`, `POST/GET /api/kitchen-orders`) — أي فرع يطلب أصناف (خام أو مصنّعة) من السنتر كيتشن.
- **تنفيذ الطلبية / تحويل** (`POST /api/kitchen-transfers/itemized`) — السنتر كيتشن يشوف الطلبيات المعلّقة، يحدد الكميات الفعلية اللي هيبعتها (ممكن تختلف عن المطلوب)، والتحويل بينزل من مخزون السنتر كيتشن ويزود مخزون الفرع المستقبِل تلقائيًا، ويقفل الطلبية "اتنفذت". تكلفة التحويل (`amount_at_cost`) بتتحسب تلقائي من `unit_cost` بتاع كل مكوّن.
- `satamoni-kitchen.html` — شاشة واحدة بثلاث تبويبات: "اطلب من السنتر كيتشن" (كل الفروع)، و"تنفيذ الطلبيات" و"التصنيع" (السنتر كيتشن/الأدمن بس، بتظهر تلقائي حسب فرع المستخدم). فيها كمان جدول "كتالوج المكونات" لتصحيح وحدة/نوع أي مكوّن بعد الاستيراد.
- **الموردين**: `suppliers` + `inventory_item_suppliers` — سجل شركات المواد الخام وسعر كل مكوّن عندهم (لمقارنة الأسعار). API: `GET/POST /api/suppliers`, `POST /api/suppliers/:id/items`.

### استيراد بيانات السنتر كيتشن من إكسل

زي استيراد المنيو بالظبط، بس للمواد الخام ووصفات التصنيع والموردين:

```bash
npm run import-kitchen-data   # بيقرأ db/seed-data/central-kitchen.json افتراضيًا
```

- بيضيف مواد خام جديدة، يحدّث نوع الأصناف الموجودة بالفعل لـ"مصنّع"، يحط وصفات التصنيع، ويسجل الموردين وأسعارهم.
- **مهم:** الاستيراد ده أبدًا مبيعدّلش وحدة قياس صنف موجود بالفعل في الكتالوج (عشان متبوظش معنى كميات موجودة في وصفات تانية). لو محتاج تصحح وحدة صنف (كتير من المواد الخام الجديدة اتحطت بوحدة "قطعة" افتراضية لعدم توفر مصدر أدق)، استخدم جدول "كتالوج المكونات" في `satamoni-kitchen.html` أو `PATCH /api/inventory/items/:id`.

## المصروفات / المشتريات / الموردين / تقفيل الكاش

بديل كامل للإدخال اليدوي بالإكسل، بنفس الجداول اللي كانت موجودة بس دلوقتي ليها API:

| Endpoint | مين يقدر يستخدمه |
|---|---|
| `GET/POST /api/expenses` | أدمن، محاسب، مدير فرع (على فرعه بس) — لازم `categoryId` من بند ثابت، مش نص حر |
| `GET/POST /api/expenses/categories`، `PATCH /api/expenses/categories/:id` | القراءة: نفس صلاحيات المصروفات — الإضافة/التعطيل: أدمن بس |
| `GET/POST /api/purchases` | أدمن، محاسب، مدير فرع (على فرعه بس) |
| `GET /api/kitchen-transfers` | أدمن، محاسب، مدير فرع (فرعه بس) |
| `POST /api/kitchen-transfers` | أدمن بس (سنتر كيتشن بيبعت بضاعة بالتكلفة لفرع) |
| `GET/POST /api/suppliers/ledger` | القراءة: أدمن/محاسب/مدير فرع (فرعه) — الإضافة: أدمن ومحاسب بس |
| `GET/POST /api/cash-sessions` | أدمن، محاسب، مدير فرع، كاشير (على فرعه) — ده تقفيل الكاش اليومي |

`POST /api/cash-sessions` بيعمل upsert بمفتاح (فرع + تاريخ)، ويحسب `expected_closing_cash` و`cash_difference` جوه السيرفر (مش بإدخال يدوي) عشان محدش يغلط في المعادلة. البيانات دي هي اللي بتغذي `/api/reports/daily` (شيت "لوحة التحكم").

`satamoni-accounting.html` — شاشة واحدة بخمس تبويبات (مصروفات / مشتريات / تقفيل كاش / كشف حساب المخزن / تحليل التكلفة)، مقفولة على فرع مدير الفرع تلقائيًا، وإضافة كشف الحساب معطّلة في الواجهة لغير الأدمن/المحاسب (بما يطابق صلاحيات الـ API).

### تكويد المصروفات (بنود ثابتة)

بدل ما أي حد يقدر يسجل مصروف بنوع نص حر (يودي لتضارب صياغات زي "صيانة"/"Maintenance" في التقارير)، بند المصروف بقى لازم يتختار من ليستة ثابتة (`expense_categories`) — الأدمن بس بيضيف بند جديد أو يعطّل بند قديم، وأي حد بيسجل مصروف بيختار من دروب داون بس. البنود الافتراضية: إيجار، مرافق، صيانة، نقل ومواصلات، تسويق وإعلانات، أدوات ومستلزمات، رسوم وضرائب، أخرى — **عمدًا من غير "رواتب"** لأن تكلفة الرواتب متتبعة بالفعل من نظام الرواتب المخصص وبتتحسب لوحدها في قائمة الدخل (تسجيلها كمان كمصروف يدوي يودي لازدواج في التكلفة).

## تحليل التكلفة وهامش الربح (بديل شيت "تحليل التكلفة والسعر")

- **`GET /api/reports/menu-cost-analysis?targetFoodCostPercent=0.375`** — لكل صنف/حجم في المنيو: تكلفة الريسبي الفعلية (من `menu_item_variant_ingredients × inventory_items.unit_cost`)، نسبة تكلفة الطعام (تكلفة÷سعر بيع)، الربح، نسبة الهامش، والسعر العادل المقترح (تكلفة÷النسبة المستهدفة). محسوب لحظيًا من غير جداول إضافية — أي تعديل في الريسبي أو `unit_cost` بينعكس فورًا. متاح لأدمن/محاسب/مدير فرع (التقرير مش مقفول على فرع لأن الريسبي والأسعار موحدة على كل الفروع).
- تبويب "تحليل التكلفة" في `satamoni-accounting.html` — جدول كامل بكل الأصناف، مع خانة تقدر تغيّر بيها النسبة المستهدفة وتحدّث الجدول فورًا.

## قائمة الدخل (نظام حسابات يسحب من الداتا الفعلية)

بدل الإدخال اليدوي لقيود مبيعات/مشتريات في شيت، قائمة الدخل بتتحسب لحظيًا من نفس بيانات النظام الحقيقية (الطلبات الفعلية والمصروفات المسجلة) — مفيش نسخ أو إدخال مزدوج للأرقام:

- **الإيرادات** = مجموع `orders.total` الفعلي للطلبات في الشهر المطلوب (بيستبعد الطلبات الملغاة).
- **تكلفة البضاعة المباعة (COGS)** — بتتاخد من `order_items.cost_at_sale`، وده عمود بيتسجل **وقت البيع نفسه** (جوه نفس الـ transaction اللي بتخصم المخزون) مش بيتحسب لحظيًا وقت التقرير. الفايدة: لو الريسبي أو تركيبة عرض/كومبو اتغيرت بعد كدة، الطلبات القديمة تفضل محتفظة بتكلفتها الحقيقية وقتها بدل ما التقرير يعيد حسابها بالريسبي الجديد بأثر رجعي. العروض بتتفكّ لأصنافها الأصلية بنفس منطق خصم المخزون بالظبط. لو مكوّن من غير `unit_cost` وقت البيع، السطر بيتعلّم `cost_at_sale_incomplete = true` والتقرير بيوريك عدد الطلبات المتأثرة بدل ما يسكت عن نقص البيانات.
- **إجمالي الربح** = الإيرادات − COGS، مع نسبة الهامش الإجمالي.
- **المصروفات التشغيلية** — من جدول `expenses` الموجود بالفعل، مجمّعة حسب النوع.
- **صافي الربح (قبل الرواتب)** = إجمالي الربح − المصروفات التشغيلية.
- **تكلفة الرواتب** — مسحوبة مباشرة من نظام الرواتب (`services/payroll-engine.js`، نفس محرك `GET /api/payroll/summary`): الصافي المستحق الصرف لكل موظف بعد السلف والجزاءات والمكافآت. **لفرع واحد بعينه**، التكلفة بتشمل موظفي البصمة اللي فرعهم الأساسي هو الفرع ده بس؛ رواتب الإدارة والمطبخ المركزي (اللي مالهاش فرع بيع محدد) بتتحمّل على **الإجمالي المجمّع بس** مش على أي فرع بعينه (عشان قائمة الدخل متبقاش مضلِّلة). **صافي الربح النهائي** = صافي الربح قبل الرواتب − تكلفة الرواتب.
- API: `GET /api/reports/income-statement?year=&month=&branchId=` (فرع واحد أو مجمّع لكل الفروع لو `branchId` فاضي؛ مدير الفرع مقفول على فرعه تلقائيًا، وبيشوف إجمالي تكلفة رواتب فريقه بس - مش تفصيل رواتب الموظفين)، و`GET /api/reports/income-statement/by-branch?year=&month=` (مقارنة كل الفروع + صف مجمّع + `payrollOverhead`، أدمن/محاسب بس).
- تبويب "قائمة الدخل" في `satamoni-accounting.html` — اختيار السنة/الشهر/الفرع (أو "كل الفروع")، عرض الإيرادات/COGS/الهامش/المصروفات حسب النوع/تكلفة الرواتب/صافي الربح النهائي، وجدول مقارنة أداء الفروع لكل من الأدمن والمحاسب.

## داش بورد المالك (كل تفاصيل الشغل في شاشة واحدة)

`satamoni-dashboard.html` — شاشة واحدة بفلتر سنة/شهر/فرع، بترجع كل حاجة من نداء واحد (`GET /api/reports/dashboard?year=&month=&branchId=`، أدمن/محاسب — مدير الفرع مقفول على فرعه لو استخدمها):

- **مؤشرات سريعة (KPI tiles)**: الإيرادات، عدد الطلبات، متوسط قيمة الطلب، تكلفة البضاعة المباعة، إجمالي الربح وهامشه، المصروفات التشغيلية، تكلفة الرواتب، صافي الربح النهائي — نفس أرقام قائمة الدخل بالظبط (بيستخدم نفس دوال الحساب `computeRevenueAndCogsByBranch`/`computePayrollCostByBranch`، مفيش ازدواج منطق).
- **رسم بياني للمبيعات اليومية** خلال الشهر (اتجاه الإيرادات يوم بيوم).
- **الأصناف الأكثر مبيعًا** (أعلى 10 بالإيراد، مع الكمية المباعة لكل صنف/حجم).
- **الفروع الأكثر مبيعًا** (كل الفروع، مرتبة بالإيراد).
- **مناطق التوصيل الأكثر مبيعًا** (أعلى 10، من طلبات الدليفري بس).
- **المصروفات حسب البند** (نفس بنود التكويد الثابتة).
- **حالة التحصيل** (محصّل / تحت التحصيل) بالمبلغ وعدد الطلبات.
- **حالة الطلبات** (تحت التحضير / في الطريق / مكتملة / ملغاة) — بتوضح معدل الإلغاء كمان.

كل الرسوم البيانية (خط، أعمدة، دونات) متعملة بـ CSS/SVG بسيط من غير أي مكتبة خارجية أو اتصال إنترنت — تشتغل بالكامل أوفلاين زي باقي الشاشات.

## مركز التقارير

`satamoni-reports.html` — شاشة تانية منفصلة عن داش بورد المالك، مخصصة لتقارير تفصيلية بمدى تاريخ حر (`from`/`to`، مش مقفولة على شهر واحد) وفلتر فرع، بـ16 تبويب. متاحة لأدمن/محاسب/مدير فرع (مدير الفرع مقفول على فرعه تلقائيًا في كل التبويبات). كل التبويبات بتتحمّل عند أول فتح ليها بس (مش كلها مرة واحدة)، وبتتحدّث تلقائي لما تغيّر الفلاتر وتدوس "تطبيق":

## العملاء (CRM) وكول سنتر

- كل طلب فيه رقم موبايل (POS/موقع/كول سنتر) بيعمل upsert تلقائي في جدول `customers` — من غير أي إدخال يدوي إضافي.
- بيانات العميل بقت أشمل: رقمين تليفون (`phone` + `phone2`)، عنوان تفصيلي (`address_details`)، منطقة توصيل افتراضية (`delivery_area_id`)، وعلامة مميزة تساعد الطيار يوصل (`distinguishing_mark`) — بتتسجل/تتحدّث تلقائيًا مع كل طلب دليفري.
- `GET /api/customers?phone=` — بروفايل عميل كامل: بياناته + عدد طلباته + إجمالي إنفاقه + آخر 20 طلب، وبيدوّر في `phone` و`phone2` معًا. بيرجع `isRegistered: true/false` — ده اللي بيرد على "بمجرد ما نكتب رقم التليفون يظهر إن العميل متسجل ولا لأ".
- `GET /api/customers?q=` — بحث بالاسم أو رقم التليفون.
- `PATCH /api/customers/:phone` — تسجيل/تعديل الاسم، الرقم التاني، العنوان، المنطقة، العلامة المميزة، الملاحظات، أو نقاط الولاء (بينشئ العميل لو مش موجود).
- `POST /api/orders` بـ `source: "callcenter"` — موظف الكول سنتر (أو الأدمن) بس، ومش مقفول على فرع واحد زي الكاشير (لأنه بياخد طلبات لكل الفروع/مناطق التوصيل).
- `satamoni-callcenter.html` — شاشة كاملة: بحث عن العميل (يظهر عدد طلباته وإجمالي إنفاقه وآخر 20 طلب وملاحظاته)، وبمجرد كتابة رقم موبايل كامل بيدوّر أوتوماتيك ويبيّن "✅ عميل مسجل" أو "🆕 عميل جديد" ويملى العنوان/المنطقة/العلامة المميزة/الرقم التاني لو موجودين، وتسجيل طلب جديد (دليفري/تيك أواي/صالة) بنفس منطق شاشة الكاشير.

## دورة حياة طلب الدليفري وحالة التحصيل

- `orders.status`: `preparing` (تحت التحضير، الحالة الافتراضية لطلبات الدليفري) → `out_for_delivery` (في الطريق، لازم اسم الطيار) → `completed` (اتسلم/رجع الطيار)، أو `cancelled` في أي وقت قبل الاكتمال. طلبات الصالة/التيك أواي بتتسجل `completed` على طول لأنها بتتحاسب وتتسلم لحظيًا عند الكاشير.
- `orders.payment_status`: مستقل عن حالة الطلب — `collected` (محصّل) أو `pending_collection` (تحت التحصيل). بيتحدد تلقائيًا وقت إنشاء الطلب: طلبات الدليفري بتفضل "تحت التحصيل" لحد ما الطيار يرجع ويسلّم الفلوس فعليًا للكاشير مهما كانت وسيلة الدفع، وطلبات الصالة/التيك أواي بتتحدد حسب `payment_methods.kind` (كاش = محصّل لحظيًا، فيزا/محفظة/آجل = تحت التحصيل لحد ما يتأكد وصول الفلوس أو تسوية آخر الشهر).
- `payment_methods.kind` ∈ `cash` | `card_or_wallet` | `credit` — بيتحدد لكل طريقة دفع من شاشة الأدمن، وبيتحكم في حالة التحصيل الأولية.
- `order_status_log` — سجل كامل بكل تغيير حالة (مين غيّرها وإمتى وملاحظة)، متاح في تفاصيل كل طلب.
- `GET /api/orders?status=&orderType=&paymentStatus=&branchId=&date=` — فلترة الطلبات بأي تركيبة من الحقول دي.
- `GET /api/orders/:id` — تفاصيل الطلب الكاملة (الأصناف + سجل الحالة بالكامل).
- `PATCH /api/orders/:id/status` — تغيير حالة الطلب (`{status, driverName?, notes?}`) — لازم اسم الطيار لما تتحول لـ"في الطريق"، ومينفعش تتعدل حالة طلب اتسلم أو اتلغى بالفعل.
- `PATCH /api/orders/:id/payment-status` — تأكيد تحصيل الفلوس فعليًا (`{paymentStatus}`).
- `satamoni-delivery.html` — شاشة متابعة كل الطلبات بفلاتر (الحالة/الفرع/حالة التحصيل)، وأزرار: طباعة تذكرة تحضير للمطبخ، خروج مع الطيار (بيسجل اسمه)، تأكيد الاستلام، تأكيد التحصيل، وإلغاء الطلب — مع سجل الحالة الكامل لكل طلب.
- `branches.supports_dine_in` — هل الفرع فيه صالة تناول داخلي، يتحكم في ظهور خيار "صالة" في شاشة الكاشير (افتراضيًا مقفول لغير الإبراهيمية، بيتغيّر من شاشة الأدمن).

## صلاحيات الخصم والاسترجاع (PIN موافقة مدير)

عشان مفيش كاشير يقدر يحط أي خصم أو يلغي أي بيع من غير رقابة:

- **PIN موافقة**: مدير الفرع/الأدمن بس يقدر يكون له PIN (4-6 أرقام، `users.pin_hash`، بيتحدد من شاشة الأدمن — "الموظفين الحاليين"). بيتستخدم للموافقة الفورية على جهاز الكاشير من غير ما المدير يسجل خروج ودخول بحسابه.
- **حد الخصم بدون موافقة**: `pos_settings.max_unapproved_discount_percent` (افتراضيًا 10%، قابل للتعديل من شاشة الأدمن). أي خصم فوق النسبة دي في شاشة الكاشير أو الكول سنتر بيفتح نافذة "دخّل PIN مدير الفرع أو الأدمن" — والسيرفر بيتأكد تاني من صحة الموافقة (مش بس بيصدّق الفرونت إند)، ومقفول على نفس فرع الطلب لو المدير مش أدمن.
- **استرجاع طلب مكتمل (Void)**: أي كاشير/كول سنتر/مدير فرع/أدمن يقدر يبدأ طلب استرجاع (`POST /api/orders/:id/void`، لازم سبب)، بس دايمًا لازم موافقة مدير فرع أو أدمن — لو اللي بيسترجع نفسه مدير/أدمن، بيوافق بحسابه على طول؛ غيره لازم PIN. الاسترجاع بيرجّع حالة الطلب لـ`cancelled` (يستبعده من الإيرادات في كل التقارير زي أي إلغاء عادي، بس بعلامة `voided = true` تفرّقه عن الإلغاء قبل التنفيذ)، **وبيرجّع المخزون** اللي كان اتخصم وقت البيع تلقائيًا (نفس منطق خصم الـ BOM بالظبط بس بالعكس). حالة التحصيل مبتتغيّرش أوتوماتيك — لو الفلوس كانت اتحصّلت فعلاً، التسوية دي بتتعمل يدويًا منفصل.
- `POST /api/auth/verify-override-pin` — `{pin, branchId}` بيرجع `{approverId, approverName}` لو الـ PIN صحيح وبتاع مدير/أدمن مسموح له على الفرع ده.
- `satamoni-delivery.html` — زرار "🗑️ استرجاع (Void)" بيظهر على أي طلب مكتمل لسه ما اتسترجعش، وبيوضح "(استرجاع)" وسبب الاسترجاع على الطلبات اللي اتسترجعت.
- **حد محاولات الـ PIN الغلط**: بعد 5 محاولات غلط على حساب موظف معيّن، `verify-override-pin` بيتقفل 5 دقايق (حتى لو الـ PIN الصح اتكتب بعد كده) — عشان محدش يقدر يجرب كل احتمالات الـ PIN (4-6 أرقام) بالتجربة. القفل خاص بكل موظف لوحده (موظف تاني مش متأثر)، وبيتصفّر تلقائي أول ما يعدّي محاولة صح.

## تأمين سعر الصنف (السيرفر مش بيصدّق سعر الواجهة)

`POST /api/orders` كان بيصدّق `unitPrice`/`priceDelta` الجايين من الواجهة زي ما هما، يعني نداء API مباشر (أو جهاز كاشير متلاعب فيه) كان يقدر يبيع أي صنف بأي سعر — حتى صفر — أو يهرّب "خصم" مقنّع في هيئة مرفق بسعر سالب يتخطى نظام موافقة الخصومات بالكامل. دلوقتي كل سطر في الطلب بيتأكد منه من المنيو الحقيقي في قاعدة البيانات قبل ما يتسجل:

- سعر الصنف/الحجم بيتاخد من `menu_item_variants.price` (أو `talabat_price` لو `source: "talabat"`)، مش من الواجهة.
- سعر كل مرفق بيتاخد من `menu_item_modifiers.price_delta` الحقيقي، مش من اللي الواجهة بعتته.
- سعر العرض بيتاخد من `combos.price`.
- الصنف/الحجم/المرفق/العرض لازم يكونوا موجودين ومفعّلين (`is_active`)، وإلا الطلب بيترفض برسالة واضحة ("الصنف ده متوقف حاليًا"، "الصنف ده مش متاح على طلبات"...).
- ده شغال على كل مصادر الطلبات بما فيها `source: "website"` (اللي أصلًا من غير تسجيل دخول، فكان أكبر خطر).

## الموارد البشرية (Shifts + Attendance)

- `GET/POST /api/hr/shifts` — جدولة شيفتات الموظفين (الإضافة: أدمن أو مدير الفرع لفرعه بس).
- `POST /api/hr/attendance/clock-in` و`clock-out` — كل موظف بيسجل حضوره/انصرافه بنفسه بالتوكن بتاعه؛ فيه حماية من تسجيل حضور مزدوج أو انصراف من غير حضور مفتوح.
- `GET /api/hr/attendance` — سجل الحضور الكامل (أدمن أو مدير الفرع لفرعه).
- `GET /api/users?branchId=` بقى متاح لمدير الفرع كمان (مقفول على فرعه)، مش أدمن بس، عشان يقدر يشوف موظفينه ويعيّنلهم شيفتات.
- `satamoni-attendance.html` — أي موظف بيسجل حضوره/انصرافه بنفسه، وأدمن/مدير الفرع كمان يشوفوا تعيين الشيفتات وسجل الحضور الكامل لفرعهم.

## نظام الرواتب (يحسب أوتوماتيك من شيت البصمة)

بديل كامل لشيت "ساتاموني - نظام حساب المرتبات الشهري" — قاعدة بيانات موظفين حقيقية، استيراد بصمة الفروع، وحساب المرتب المستحق أوتوماتيكيًا بنفس قواعد الشيت الأصلي بالظبط (اتفحصت كل قاعدة على حدة رقميًا مقابل بيانات حقيقية من الشيت). ده نظام منفصل تمامًا عن `users`/`shifts`/`attendance_records` (اللي خاصة بحسابات الدخول على شاشات النظام) - `employees` هنا هي قاعدة الرواتب الكاملة (أغلب الموظفين مالهمش حساب دخول أصلًا - شيفات، سائقين، عمال مطبخ...).

- **`employees`** — سجل كل موظف: القسم والوظيفة، نظام الحضور (`fingerprint_auto` بصمة تلقائي / `manual` يدوي للمطبخ المركزي / `none` بدون تتبع للإدارة والحسابات)، الراتب الأساسي أو أجر الساعة، أيام العمل بالشهر، الشيفت (يحدد وقت الدخول الافتراضي لحساب التأخير)، وخيار "احسب الراتب من فرع واحد بس" للموظف اللي بيتنقل بين فروع.
- **`employee_fingerprint_codes`** — كود بصمة الموظف عند كل فرع (ممكن يكون له كود في أكتر من فرع).
- **`attendance_punches`** — بصمات الدخول/الخروج الخام المستوردة من تصدير جهاز البصمة. **يوم بدون سطر = إجازة تلقائيًا** (بيتولّد شبكة كل أيام الشهر ويتعمل عليها LEFT JOIN مع البصمات الفعلية، فمش محتاج صفوف فاضية لكل يوم زي الشيت).
- **حساب اليوم الواحد** (`services/payroll-engine.js`): دقائق التأخير (وقت الدخول − وقت الدخول الافتراضي حسب الشيفت)، حالة اليوم (حاضر/إجازة/نسيان بصمة دخول أو خروج)، نسبة خصم التأخير من سلم `late_deduction_tiers` القابل للتعديل، **إعفاء تلقائي لأول N مرة تأخير حقيقي كل شهر لكل موظف** (`allowed_late_exemptions`، عداد بالتسلسل الزمني)، وخيار إعفاء يدوي (`exempted`) لأي يوم بعينه. هدر الساعات والأوفر تايم بيتحسبوا من مقارنة ساعات العمل الفعلية بالشيفت القياسي.
- **حساب الشهر الكامل**: 4 أيام إجازة مدفوعة شهريًا (قابلة للتعديل) — لو الغياب الفعلي تعدّاها بيتحول لخصم غياب حقيقي بسعر يوم العمل، ولو الموظف حضر أكتر من المطلوب بياخد مكافأة أيام عمل إضافية بنفس السعر. الموظف بأجر الساعة (`wageType: "hourly"`) بيتجاهل الراتب الأساسي تمامًا ومرتبه = مجموع ساعات العمل الفعلية × أجر الساعة.
- **موظفي المطبخ المركزي** (`central_kitchen_manual_attendance`) — إدخال شهري يدوي لكل موظف (أيام حضور/غياب/دقائق تأخير/خصم إضافي بالجنيه مباشرة)، بديل شيت "حضور المطبخ المركزي (يدوي)".
- **السلف والجزاءات والمكافآت** (`payroll_adjustments`) — بتتخصم/تتضاف على المرتب المستحق بعد الحضور عشان توصل للصافي النهائي.
- كل الحساب المالي (ضرب/تقريب) بيحصل جوه SQL بـ `NUMERIC` أو بحساب القرش الصحيح في JS (زي باقي النظام) عشان محدش يتصرف فلوس غلط بسبب دقة الأرقام العشرية.
- API (أدمن ومحاسب بس - رواتب بيانات حساسة وشاملة كل الفروع): `GET/PATCH /api/payroll/settings`, `PUT /api/payroll/late-tiers`, `GET/POST/PATCH /api/payroll/employees`, `PUT /api/payroll/employees/:id/fingerprint-codes`, `POST /api/payroll/attendance-punches/import`, `GET/PATCH /api/payroll/attendance-punches` (لمراجعة وتصحيح البصمات الناقصة أو تفعيل إذن تأخير)، `GET/POST /api/payroll/central-kitchen-attendance`, `GET/POST/DELETE /api/payroll/adjustments`, `GET/POST /api/payroll/department-sales`, و**`GET /api/payroll/summary?year=&month=`** (الملخص المحسوب الكامل لكل موظف).
- `satamoni-payroll.html` — شاشة كاملة بخمس تبويبات: ملخص الرواتب المحسوب، الموظفين (إضافة وربط أكواد البصمة)، استيراد وتصحيح البصمة (لصق بيانات الجهاز مباشرة)، حضور المطبخ المركزي، والسلف/الجزاءات/المكافآت.

### استيراد بيانات الرواتب الحقيقية من إكسل

زي استيراد المنيو بالظبط، بس للموظفين وبصمة يوليو 2026:

```bash
npm run import-payroll-data   # بيقرأ db/seed-data/payroll-data.json افتراضيًا
```

- بيستورد 64 موظف حقيقي (بأكواد بصمتهم لكل فرع)، بصمات الفروع التلاتة كاملة ليوليو 2026 (1270 سطر)، حضور المطبخ المركزي اليدوي، والسلف/الجزاءات/المكافآت (48 قيد) - كل ده من شيت "ساتاموني - نظام حساب المرتبات الشهري" الأصلي.
- بينشئ الفروع (الإبراهيمية/العصافرة/محرم بك) لو مش موجودة بالاسم بالفعل، أو بيستخدم الموجود من غير ما يكرره.
- **آمن تكراره** — التمييز بين الموظفين بـ(الاسم + القسم + الوظيفة)، والسلف/الجزاءات بمقارنة القيد بالكامل قبل الإضافة.
- **15 صف اتقفلوا عمدًا** — أكواد بصمة ظهرت في الجهاز بدون بيانات HR مكتملة (قسم/وظيفة) في الشيت الأصلي؛ نفس التنبيه اللي كان في الشيت ("⚠ موظف جديد محتمل") - محتاجين تكميل يدوي بدل ما نستوردهم ببيانات ناقصة/مخترعة.

## ملاحظة مهمة

النسخة دي لسه MVP، وخطة Render المجانية معمولة للتجربة بس. قبل أي استخدام فعلي في الإنتاج (بيانات حقيقية وعملاء حقيقيين)، لازم كمان نضيف/نراجع:
- ترقية لخطة مدفوعة (السيرفر المجاني بينام، والداتابيز المجانية بتتحذف بعد 90 يوم)
- نسخ احتياطي دوري لقاعدة البيانات
- Rate limiting على `/api/auth/login` عشان يمنع محاولات تخمين الباسورد (الـ PIN بقى له حد محاولات، الباسورد لسه من غيره)
- مراجعة أمان قبل فتحه لعملاء حقيقيين (HTTPS متوفر تلقائي على Render)
- **الفاتورة الإلكترونية الضريبية (ETA)** — المطعم مسجّل في منظومة القيمة المضافة، فده متطلب قانوني حقيقي لسه مبنيش: لازم كل فاتورة بيع تتوقّع رقميًا وتترفع لمصلحة الضرائب المصرية (E-Invoice API) وقت الإصدار، مش تقرير مجمّع آخر الشهر. محتاج تكامل منفصل قبل أي استخدام فعلي في الإنتاج.
- اختبارات آلية للسيستم (regression tests) — كل التحقق دلوقتي يدوي (psql/curl/متصفح) وقت كل تعديل؛ من غير اختبارات آلية، تعديل جديد ممكن يكسر حاجة قديمة بصمت (زي ما حصل مع مزامنة الفروع لما تعديلات لاحقة كسرتها من غير حد ينتبه).
